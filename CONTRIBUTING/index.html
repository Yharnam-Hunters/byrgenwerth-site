Contributing

Tonight, Gehrman joins the hunt.Gehrman, the First Hunter

Paleblood is open to everyone. This is the short version: how to help, your first pull request, and the rules.

Ways to help

Track What you do
Name functions Good first issues: name small, clear functions in the shared function table.
Document a system One page here per system.
Replace functions Readable C++ replacements, verified and reviewed.
Build the runtime Implement PS4 system calls in RT_SYSLIB. No dump needed.
Tooling The harness, the capture library, the Ghidra scripts.
More on each track
  • Name functions — the good first issues: small functions with a clear purpose, identified from their callers and the library calls they make, named in the shared function table.
  • Document a system — a page here per system: summary, key functions, structures, patch points, open questions.
  • Replace functions — readable C++ replacements, verified against the original with the harness and reviewed independently.
  • Build the runtime — claim a call or tightly related group in its system issue (#34–#41), then use a runtime/<function> branch to implement it in runtime/syslib/<group>.c, registered with RT_SYSLIB. All eight system issues were closed on 11 November 2026, with every call the game imports answered; check the open runtime issues for new work before you start. Its tests go in a file of their own, test/syslib/<group>.c, as SYSLIB_TEST(name) { ... } blocks, so parallel pull requests do not edit the same lines (#407); the PR checks count those files as runtime tests (#430). Runtime-only work is clean-room, needs no game dump or captures, and receives maintainer boot verification after merge. Independent reverse engineering may include the system libraries of your own console's firmware: name each by its SHA-256 in the runtime report, take only facts from it, write your own code, and never copy, attach or link the files (#356). See the runtime syscall notes and the full workflow in Paleblood's contribution guide.
  • Tooling — the harness, the capture library, the Ghidra scripts.

Your first pull request

  1. Fork. Fork Paleblood and run tools/install_hooks.sh in your clone.
  2. Set up. Decompilation: follow ONBOARDING.md. Runtime: claim a function in its system issue (#34–#41) on a runtime/<function> branch.
  3. Keep it small. One function or tightly related group per PR, with its tests in test/syslib/<group>.c and a runtime report.
  4. Merge. CI runs without a dump. After merge, a maintainer boot-tests it and posts the result.
Each step in full
  1. Fork Paleblood on GitHub and run tools/install_hooks.sh in your clone.
  2. For decompilation, follow ONBOARDING.md from your own dump to Ghidra. A draft from tools/draft.sh is a starting point; it marks with ; GAP: and decodes the code Ghidra leaves out after a call it wrongly treats as not returning (#189). For runtime work, read the syscall notes and claim one function or related group in its system issue (#34–#41); use a branch named runtime/<function>.
  3. Keep one function or tightly related group per PR. Put its RT_SYSLIB tests in their own file, test/syslib/<group>.c (test/syslib/np_trophy.c is an example; cases already in test/test_syslib.c may be updated there), and include evidence, confirmed behavior, unresolved questions, and test results in the runtime report. For a decompilation PR, tools/session_report.py --verify takes the output folder of a tools/verify.py run (or the summary.json it writes there) and adds its results to the session report (#417). A change to a function family takes the summary.json of a clean tools/verify.py family run the same way: the report lists each changed family, and CI refuses a family change without one (#515).
  4. To bring your branch up to date, merge origin/main into it; the push gate checks only the commits main does not have yet (#407).
  5. Runtime-only PRs run the compiler matrix, RT_SYSLIB tests, and repository policy checks without requiring a dump, captures, or function-level verify.py. CI also builds and tests each pull request merged with every other open one (the combined job, #136), so two changes that break only together are caught before either merges. After merge, a maintainer runs tools/boot.py locally and posts the result on the PR.
  6. However you work, the workflow is the same; tools/handoff.py writes a shareable handoff of where a piece of work stands, so someone else can pick it up (#93).

Your own copy

Decompilation needs your own PS4 and your own copy of the game. Runtime work needs no game files. The project never provides them.

Your own copy in full

Decompilation work starts from your own console and your own copy of the game: Bloodborne (CUSA03173, EU) with the 1.09 update, dumped from your own PS4. Runtime-only contributions do not need a dump, captures, or any game files. The project does not provide or point to game files, pkgs, firmware, keys or decryption tools. Requests for game files, or links to them, are removed wherever they are posted, and may lead to a ban.

Ground rules

  • No game files. Ever.
  • No game media in the code repository.
  • Verified and readable before it is done.
  • Say how you know.
  • One pull request per function or cluster.
The ground rules in full
  • No game files. Ever. No executables, assets, decompiler output or extracted data in commits, issues, pull requests or Discussions.
  • Keep game media out of Paleblood's code repository and its issues, pull requests, and Discussions. The hook and CI refuse image and video files (by extension and by contents). The only images allowed there are under docs/assets/ and listed in docs/assets/ALLOWLIST with the command that produced them, and they are our own work: recordings of our tools' output, and frames drawn by Paleblood's own renderer, at full resolution, added by the maintainer with attribution (the README shows one, the newest milestone frame, #610). Every file there is capped at 2 MiB; an allowlisted image may be up to 8 MiB, so a frame is posted whole (#550). Contributors do not add game frames themselves; propose one in an issue instead. The documentation site follows a separate, asset-by-asset review process for technical and critical context; attribution or educational purpose alone does not establish permission. See Evidence & Media Review.
  • Verified and readable. A replacement that "looks right" is not done until the harness finds no difference on recorded and edge cases, deliberately wrong versions fail, it reads well (the code repository's STYLE.md), and an independent reviewer has approved it.
  • Matching (optional, since #660). For small C-style functions, tools/match.py compiles your C with upstream clang 3.4.2 and the PS4 SDK's publicly documented flags and compares the result byte for byte with the original in your own dump; the result goes in symbols/matching.csv. Like verify.py it runs only on your machine. A byte-exact match can stand in for the recorded cases verified needs; the edge results and the independent review are still required. Sony's own compiler is never used, matching C is written from your own understanding of the function, never from decompiler output, and large C++ engine functions are not worth chasing. Paleblood's docs/MATCHING.md has the details.
  • The local promotion tool reruns the recorded and edge suites before changing a function to verified; its comparison output is temporary and kept away from the capture library. Case data stays on the contributor's machine.
  • Say how you know. When you name a function, say how you inferred what it does: its callers, its library calls, the memory it touches. A name says what is known and no more.
  • One pull request per function or cluster, with the disclosures CONTRIBUTING.md asks for.
