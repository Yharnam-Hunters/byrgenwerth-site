Architecture

How Paleblood fits together: two tracks, decompilation and runtime, and how a function moves from original code to verified, readable C++.

At a glance

Paleblood is a decompilation with its own runtime. The decompilation rewrites the game's code, function by function, as readable C++ that is proved to behave like the original. The runtime is what that code, and the original executable while it is being replaced, runs on: Paleblood's own loader and a growing set of PS4 system-call implementations. The game does not run on Paleblood's runtime yet; the Runtime page has the roadmap, implemented calls, and the latest saved boot result.

Full game runs still use an external host scaffold while the project-owned runtime is completed. The verification harness independently maps the executable and replays recorded inputs. Its capture writer now supports stable, function/run-identified output and replay checks, but it has no production call sites yet and does not automatically provide new game inputs. Paleblood also has a project-owned implementation of the version-1 hook callback. A synthetic executable-memory test verifies that its jump reaches a replacement, but the callback is not yet wired into the full game-run scaffold and does not establish full-run equivalence.

The decompilation track

A replacement lives in the code repository's game/<system>/ and is written to its style rules: the objects a function touches described as structures with named fields, the original's other functions and globals reached through named declarations instead of addresses, named constants, and no test plumbing inside the game's code. A function reaches the main branch only when it is both verified and readable, and an independent reviewer, not the author, has checked both.

Replacements are registered in a hook table. When the runtime runs the game, each registered function's entry will jump to its replacement, so every caller lands in the new code: a 14-byte jump, which is why a function shorter than that cannot be hooked this way.

The runtime track

Paleblood's loader maps the game's executable, together with the game's own C library and file system modules, applies every relocation and binds every system import, to one of those modules or to the runtime's own implementation. The boot harness starts the guest startup sequence and stops at the first system function the runtime does not implement yet, naming it. The latest saved trace stops in the game's bundled libc before the executable reaches its first boot milestone. Each step of the runtime's work implements what the boot stops at, written clean-room from public documentation and our own reverse engineering.

The frame pipeline

The first system decompiled. Solid boxes are verified C++; dashed boxes are still original code.

Once per frame the frame step checks that the window is running, creates the SprjFlipper on the first frame (its constructor reads Game.FlipMode), lets the flipper's limiter wait out the frame, and runs the game's task update. The full walk-through is in How the Frame Limiter Works.

Verification

A replacement is checked against the original outside the game. The harness maps the executable from your own dump with Paleblood's loader, scripts every library call the function makes, runs the original and the replacement on the same inputs, and compares ABI-selected return values, callee-saved registers, final bytes in declared memory regions, and scripted library calls. The inputs are cases recorded in earlier game runs (the capture library) and edge cases generated for the corners. Deliberately wrong versions of the replacement must fail; if one passes, the cases are too weak and get fixed first. A function whose code no recording reaches yet is edge-verified; it becomes verified once recordings for it exist and pass, and the independent review has approved it.

What the automated tools can establish

The merged differential engine adds deterministic fixture replay, bounded input exploration, mismatch minimization, and portable evidence reports. Its tests prove infrastructure behavior using synthetic instructions; they do not establish a new game function's semantics or promote a function automatically.

Optional Linux instruction tracing observes supported guest memory reads and writes at byte granularity, including unaligned accesses, aliased pointers, and writes that leave the same value. It records the instruction, access range, before/after bytes, and register context. The support matrix defines its limits: classified string/repeat, vector-memory, atomic, and system instructions fail closed; host code outside the instrumented ranges leaves an explicit gap. Capstone does not identify every architectural implicit-memory operation, so completeness applies only to the audited instruction families.

The first differing recorded memory event is a bounded diagnostic. Original and replacement code may take different instruction paths, and an internal trace difference with equal observable results is not treated as a behavior mismatch. The tool does not claim an exact first divergence of every register at every instruction.

Coverage and the candidate pipeline

Supported instruction traces record executed basic blocks and outgoing edges per fixture. Complete traces can prioritize seeds that found new edges or a conditional outcome whose other outcome is still unseen. Partial and unavailable coverage remain explicit and cannot feed that ranking. This describes observed fixture paths, not a complete static map of every possible path.

The opt-in automation prototype connects catalog qualification to an isolated worktree, local recorded fixtures, both compiler builds, differential tests, repository checks, and a reviewable draft pull request. It accepts a prewritten clean-room replacement patch; source generation is not automated.

Gate Evidence required
Candidate Fresh ownership checks, replacement-development qualification, exact executable identity, and documented ABI.
Fixtures Recorded-game provenance and sufficient matching cases; generated boundary cases supplement those recordings.
Execution Matching observable results, complete supported instruction traces, valid memory accesses, and eligible CFG coverage.
Delivery Compiler and repository checks, a reproducible evidence report, then GitHub CI and human review.

Missing evidence rejects the run. Dry-run mode performs local work only, and a regression canary cannot open a function PR. No complete real-game candidate-to-PR run has been established by the merged evidence. Synthetic pipeline success does not change the verification counts.

Addresses

Every address in this wiki is a PS4 virtual address with the executable at 0x400000, the convention of the community patches. See Ghidra & PS4 Quirks.

Import-boundary observations

Merged PR #85 adds bounded snapshots of registers and selected stack/fixture-buffer bytes at recognized harness import entry and return. They expose net changes at that boundary; they do not trace host instructions, establish argument types, observe every memory access, or prove host control-flow coverage. Comparison, automation acceptance and coverage feedback continue to reject external-execution evidence even if another label incorrectly calls the trace complete. These diagnostics cannot qualify a function for verification, and the import-dependent clock regression remains incomplete.
