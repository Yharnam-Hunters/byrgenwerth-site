Port Architecture

How Paleblood runs the game today, and how a function moves from original code to verified C++.

At a glance: dump → scaffold → hooks → game

The game is not rebuilt from scratch and then started. It runs from the first frame as the original executable, loaded natively on a PC by a runtime scaffold, and functions are swapped for C++ one at a time while it keeps running. Every replaced function is one less piece of original code; the endpoint is a game with no original code left.

The scaffold: bbport

The scaffold is a private fork of bbport, a native Linux port of Bloodborne 1.09 by deadinside28. It converts the executable offline into a flat memory image, links in the game's own libc and Fios2 modules, binds every PS4 library import to a small runtime written for this game, and renders through a renderer derived from shadPS4. The game's x86-64 code runs directly on the CPU: there is no emulation.

Our fork adds one thing: a game library. With BB_GAME_LIB set, the loader loads libbbgame.so after relocating and patching the image and before any game code runs, and calls its bbgame_init.

The hook layer

bbgame_init reads the hook table generated from game/hooks.csv and asks the loader to write a hook at each original function: a 14-byte absolute jump to the C++ replacement. From then on every caller, wherever it is in the game, lands in the replacement. The replacement reaches game memory and other game functions through PS4 addresses (rt::ptr, rt::fn), and calls PS4 library functions through the game's own thunks, so the scaffold answers them exactly as it answers the original.

Two rules keep this safe: a function shorter than the jump cannot be hooked, and nothing may jump into the bytes the hook overwrites. The loader refuses the library when the scaffold's executable check is skipped, because every address is only valid for the one executable both projects pin.

The frame pipeline

The first system replaced. Solid boxes are verified C++; dashed boxes are still original code.

Once per frame the frame step checks that the window is running, creates the SprjFlipper on the first frame (its constructor reads Game.FlipMode), lets the flipper's limiter wait out the frame, and runs the game's task update. The full walk-through is in How the Frame Limiter Works.

Verification

A replacement is checked against the original outside the game. Replacements record their inputs during real game runs into a capture library; hand-written edge cases cover the corners. The harness maps the executable from your own dump, scripts every library call the function makes, runs the original and the replacement on the same inputs, and compares return values, callee-saved registers, every byte written and every library call. Deliberately wrong versions of the replacement must fail; if one passes, the cases are too weak and get fixed first. A function is verified only after that and a game run with it in place.

Addresses

Every address in this wiki is a PS4 virtual address with the executable at 0x400000, the convention of the community patches. bbport's own logs use offsets from 0 (subtract 0x400000). See Ghidra & PS4 Quirks.
