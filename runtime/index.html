Runtime

Paleblood is building a runtime of its own. A runtime is the software that loads a program and provides the system services it expects.

At a glance

Works
An ELF loader and boot harness load the executable and bundled modules, bind imports and run the entry point. Since 6 November 2026 Paleblood's own renderer draws the studio logos and the title screen ("Play Online / Play Offline") natively (#441, #442). With scripted input (#447) the maintainer's local runs go on past the title: save data is created, the main menu appears, and New Game reaches the first-run Brightness and Controls screens and then the opening cinematic, the first 3D scene, with pull requests still in review applied (Milestones).
Stops at
Nowhere, since 6 November 2026 (#408): no system call stops the boot, and the game keeps running until the harness's time limit. Without input it waits at the title screen. In local runs with input, the next stops are in the renderer: each menu needs drawing features the renderer stops on by name until they are added (#457, #471).
Full game
Still runs on a third-party host scaffold; the project-owned runtime has not replaced it.

The project has an ELF loader and boot harness that can load the game's executable and bundled system modules, bind imports, and run the entry point until it reaches a call the current runtime does not implement.

That is different from running the full game. Full native game runs still use a third-party host scaffold for the broader execution environment, system-library coverage, and Vulkan rendering. Since 4 November 2026 Paleblood targets macOS as well as Linux (#292): graphics are rebuilt on Vulkan on Linux and on Metal on macOS. Linux stays the primary platform and the one CI tests; macOS support is in progress. Paleblood supplies a project-owned hook plug-in and host interface, but the project-owned runtime has not replaced that host or passed equivalent full-run checks.

What works in Paleblood's runtime

ELF loading and boot diagnostics. runtime/loader.c maps the executable and bundled modules, applies relocations, and binds known imports. runtime/boot.c and tools/boot.py run the entry point and record how far it gets.

System calls. In the last recorded boot (#443) the runtime itself implemented 234 of the 686 system imports (the bundled modules supply 219 more); the calls merged since (below) are counted at the next recorded boot. They cover threads, locks and semaphores, memory, clocks, the console's start-up services, the controller, save data and trophies, the network, HTTP and PSN libraries offline, sound and movies, and reading the game's own files. On 10 November a batch added file renames, truncation and folders (#449, #458), deleting a save (#459), thread join, detach and once (#460), timed locks (#464), unmapping and protecting memory (#467), signal masks and thread names (#469), time zones and RFC 2822 dates (#466), the formatted output the file library uses (#468), the pad's motion settings and an unplugged mouse (#462), and more offline PSN and network answers (#450, #451, #461, #465). The runtime system-call notes explain each group, and end with a list of every call the runtime answers, generated from the code on every sync.

Where the PS4's behaviour is not established, the runtime does not guess: it stops and names the call. It never contacts a network. It decodes the game's sound and can play it (#398, #406), plays the game's movies (#419, #420), reads a real controller and keyboard (#431), and draws the game's logos and title screen with its own renderer (see The renderer).

Three kernel details followed on 6 November, each found by a boot that stopped there: a semaphore created for priority order now wakes its most urgent waiter first instead of stopping when a second thread waits (#426; before, some boots stopped there and others did not, depending on thread timing); a memory-protection query also answers the mapping's start and end (#422); and a second map of the same memory with the "no-overwrite" flag is accepted (#423). The movie code needs the last two.

Movies. The game plays its movies through the console's movie player library. The runtime answers all 16 of its calls (#419) and decodes the movies with FFmpeg on your computer, on a thread of its own a few frames ahead; the game receives finished pictures and sound on the movie's clock. The movie's sound port (1024 samples, 16-bit, up to 8 channels) followed in #420. FFmpeg is optional when building: without it, opening a movie stops by name.

Controller input. With --input host (and a window, --display window) the runtime reads your first gamepad and the keyboard through SDL3 and fills in the game's controller state: buttons, sticks, triggers, touch pad and vibration (#431). The default is --input none: one controller at rest, so recorded boots and CI see the same state every time. For unattended runs, --input-script plays timed button presses (#447). In the maintainer's local runs it selects "Play Offline" on the title screen and the game creates its save data. That needs sceKernelWrite, which contributor @EzequielRindello is implementing in #444 (merged on 10 November; the earlier local runs applied it from review), then sceKernelFtruncate and sceKernelRename (#449).

Function replacements and hooks. The project's plug-in receives the guest image and a hook-install callback, then registers its function replacements. Paleblood now also provides a small implementation of the version-1 hook callback:

  1. it checks the requested function range;
  2. it writes a jump to the replacement.

A synthetic executable-memory test confirms the patched entry reaches the replacement. The callback is not connected to the full game-run scaffold, and the test does not run the game.

Recent loader work (by evill33t, 3–4 November 2026): the loader also accepts the separate read-only-after-relocation segments some system modules carry (PT_SCE_RELRO, #217; none of the game's own files has one), and guest memory is reserved at its address without replacing anything already mapped there (#220). For macOS, the runtime's table of system calls can now also be built in the Mach-O format macOS uses (#216), and the loader can rewrite thread-pointer loads to a non-zero offset (#218), which the macOS thread-data work needs. That thread-data library now builds in the normal macOS configuration (#214), and a standalone Metal unit that draws offscreen is the start of the Mac display (#318, from #213). Both are by @evill33t and are compile-tested on macOS in CI.

The runtime's own boot harness can now load the decompilation's replacements too (#225, by @evill33t): pbboot takes --game-lib with the compiled game library and runs its set-up before the game's first code, so finished replacements run in place of the originals during a boot. Without the option the boot runs the original code only, as before.

How far a boot gets

6 to 10 November 2026: past the title (local runs). With scripted input (#447) and the display on, the maintainer's local runs select "Play Offline". The game creates its save data (with #444, then in review and since merged, applied for sceKernelWrite, and #449), and after the renderer learned 8- and 16-bit buffer formats (#457) it shows its main menu (New Game, System, Log In) for over a thousand frames. Choosing New Game needed depth and stencil tests that read the buffer (#471); with it, and with #470 (compute queues' buffers, in review) also applied, the boot reaches the first-run Brightness screen and then Controls, and runs on waiting for input. Scripted on past Controls, the next scene's draws needed image descriptors loaded behind a branch (#474), two-channel 8-bit images (#476) and samplers with anisotropy fields but plain filters (#477); with them the game's opening cinematic, its first 3D scene, draws. These are local observations, not saved records; the frames are on the Milestones page.

6 November 2026: the logos and the title screen. Later the same day, Paleblood's own renderer began drawing what the game asks for (see The renderer). In the maintainer's local runs (display on, with the game library from the decompilation), the boot shows the three studio logos, "Sony Computer Entertainment presents", "JAPAN Studio" and "FROM SOFTWARE", and reaches the title screen with its "Play Online / Play Offline" menu at about frame 480, with no stop within 90 seconds (#441, #442). Compared with reference frames captured locally from another PS4 runtime, the JAPAN Studio and FROM SOFTWARE frames are pixel-identical, and the title frame differs in 0.7% of its pixels, by at most 13 levels, where the menu's highlight is animated. These are local observations, not a saved record; the frames are on the Milestones page. The boot recorded on merged main afterwards (#443) runs with the display off: first flip, 243 imports called, 234 of them answered by the runtime, and nothing stops it.

Earlier on 6 November: no call stops the boot (#408). The boot recorded on merged main calls 243 imports, 218 of them answered by the runtime, and keeps running until the harness's 30-second limit. The round of runtime work merged on 5 and 6 November answered every call between the first flip and the game's main loop:

  • the install service (PlayGo, #370): every part of the game is installed;
  • the user's name and events (#372), and one controller at rest (#373);
  • the clock and calendar (#378, #379);
  • the offline PSN calls: the title id, sign-in state, matchmaking start-up, NAT and HTTPS options, network waits (#380, #381, #382, #385, #386);
  • file details and the error variable (#376), thread exit (#389, #399), add-on content (#392), the boot splash and system status (#396);
  • save data in a folder you choose (#402), and trophies, kept offline with your save data (#405);
  • the graphics packets the stand-in skips safely (#375, #377, #395);
  • sound (#398, #406). The game's audio is ATRAC9, decoded with LibAtrac9 (MIT, by Alex Barney, included unmodified in Paleblood), and with --audio host it plays through your computer's sound output.

In the maintainer's local runs with the display on, the game's main loop then runs at its own 30 frames a second, and its music and sounds start after about 17 seconds. These are observed local runs; the saved boot record shows only that nothing stops the run. At that point the frames were still black; the renderer work merged later that day draws them.

Earlier, 4 November. The boot recorded on 4 November 2026 (#304) reached the video out milestone, 6 of 8: the game's threads, its files, input and its sound system start, and it opens its display. Its first GPU work now goes through a temporary stand-in (#302), its network worker polls offline (#303), and it calls 135 imports. Its scratch files go to a writable /data folder (#308). Since #310 it gets through all eight milestones: it hands its first frame's work to the GPU and flips it to the display, then carries on to the PS4's install service (PlayGo), calling 170 imports. Nothing is drawn: the GPU work goes through the temporary stand-in described below.

The boot before it (19 October) stopped much earlier, at scePthreadAttrGetaffinity inside the game's bundled C library. #207 replaced the C library's probe that made that call, so the call is no longer made (Runtime syscalls), and the runtime work merged since covers everything up to the graphics.

Before this, the maintainer used local discovery boots that stood in for the missing pieces (the affinity query and the reader-writer locks) without committing them, to see which call comes next. On 30 October 2026 a local discovery boot:

  • started the game's threads, its HTTP client (offline) and its sound system;
  • found and read its first data file, sprj_mixer.fev, from the person's own copy;
  • stopped at the first graphics-driver call whose answer is not established (sceGnmValidateCommandBuffers).

Each call it passed through was then implemented and merged with its own evidence (the runtime system-call notes list them), and the genuine boot of 4 November now reaches the same point on merged main alone.

Capture and replay

Paleblood has a local capture writer and replay verifier.

  • Saved cases carry function and run identifiers and use stable buffer ordering.
  • Replay checks reject a case for a different function or address.
  • The version-1 production hook interface does not observe function returns or describe pointer buffers, and current replacements do not call the recorder.

A separate test adapter proves that explicitly described synthetic inputs can be serialized and replayed. This checks the case format and verifier path only. It does not capture real game calls, prove a replacement against a real recording, or supply production run inputs. tools/promote.py consumes existing recorded cases and generated edge cases; it does not create captures.

The merged differential tools can now replay fixtures, observe supported guest instruction memory accesses, collect bounded control-flow coverage, minimize mismatches, and coordinate an opt-in candidate workflow. Unsupported instructions and skipped host-call bodies reject the trace; synthetic automation tests establish tool behavior only. The Architecture verification guide explains what is observed and which stages still require original-game evidence and human review.

The GPU, for now. The first graphics calls are answered honestly for a runtime with no GPU (#297, #299): there is no debug-validation layer, no hardware state to set up, and the reserved command space is filled with no-op packets. When the game first hands work to the GPU (sceGnmDingDong), a temporary stand-in (#302) completes it at once. It runs no shaders and draws nothing: it only writes each job's "work done" value, which is what the CPU waits for, and frees the queue. This was a maintainer decision of 4 November 2026, so that start-up can continue while the engine's own renderer (its GX framework) is rebuilt to replace it (issue #39). See Runtime syscalls.

Scratch files. The engine maps its temp: and title: drives to /data and creates a fresh cache file there at start-up. The runtime now serves /data as a writable folder of its own choosing (#308): each boot gets a new, empty one, so runs start alike.

Memory the GPU can reach. The game stores GPU buffer addresses in a shortened form that only holds addresses below a fixed limit (the GPU's 40-bit address space). Memory the runtime placed higher lost its top bits there and crashed the game, so the runtime now places the memory it chooses an address for below that limit (#310).

The first frame. The game's first frame hands the GPU shader settings, draws, cache steps, waits and "work done" markers. The temporary stand-in performs the "work done" writes, checks the waits already hold, and skips the rest, then flips at the next 60 Hz tick (#310). At the time nothing was drawn; the renderer now runs the drawing work alongside it (see below).

What blocks it now. No system call does: since #408 the boot runs until its time limit, and since #442 the maintainer's local runs draw the title screen. With scripted input (#447) those runs now get past it to the main menu and the first-run settings screens (see above). What stops them next is the renderer: each new screen uses drawing features it does not have yet, and it stops by name on them. The saved boot record has not been re-recorded since #443, so it does not show any of this yet. The temporary stand-in described above still answers the GPU's "work done" values; with the display on, the renderer also runs the drawing work.

The renderer

Bloodborne draws through its own engine renderer (the GX framework) and Sony's GPU helper library compiled into the game. Its shaders ship as compiled AMD GPU code. On 4 November 2026 the maintainer chose how Paleblood draws them: - Draws: the game's own drawing functions are hooked like the rest of the decompilation, and send their work to Vulkan on Linux and Metal on macOS. - Shaders: each one is translated from AMD's code to Vulkan's or Metal's shader language when it loads, on your machine. The translator is written from AMD's public instruction-set manuals, not from any emulator. Nothing translated is published. - Ruled out: replaying the finished GPU commands, which would be GPU emulation.

Where it stands (6 November 2026). The renderer now draws the game's logos and its title screen. When the game's GPU library sets up a draw, the call is reported to Paleblood's renderer, which translates the shaders involved and draws on a PC GPU with Vulkan. In the maintainer's local runs this produces the three studio logos and the title screen, and the title frame matches a reference capture to within 0.7% of pixels (#442). It needs the display on (--display headless or window) and the game library built from the decompilation (--game-lib), because the reports come from its replacements. Since then the menus after the title draw too in local runs with scripted input: the main menu after #457 (8- and 16-bit buffer formats) and the Brightness and Controls screens after #471 (depth and stencil tests that read the buffer, stencil steps, a depth target larger than the colour target). Past them, the opening cinematic's first 3D frames draw too (#474, #476, #477). Character creation and the playable game have not run yet.

The work comes in four phases (Paleblood's docs/RENDERER.md):

  1. Display (done, #313): every frame buffer the game registers gets a frame of its own, and each flip shows it, in a window (SDL3 and Vulkan) or captured to image files for tests. Since 6 November the renderer draws into them.
  2. Shader translator (begun, #316): a decoder for GFX7, the PS4 GPU's instruction set, names every instruction. Its opcode table is generated from AMD's manual and LLVM's AMDGPU assembler, which must agree. A census of your own copy's shaders shows the game uses only 175 distinct instructions, and the decoder knows all of them. The first translation to Vulkan shaders works (#319): simple compute shaders (arithmetic, compares, conversions, buffer and constant reads and writes) run on a real GPU and give exactly the results AMD's manual defines. Since #330 it also handles branches, loops and GCN's active-lane mask: only the lanes that are switched on write results or touch memory, as on the console. Since #332 it also reads and writes typed buffers, which nearly half of the game's shaders use. Every typed access in the game uses plain 32-bit floats, so those translate exactly; any other format is refused rather than guessed. Since #333 it translates vertex and pixel shaders too: their outputs (positions, values passed down to pixels, colours) and the pixel shader's blended inputs. A translated pair already draws a test triangle on the GPU with every pixel checked, and most of the game's vertex shaders now translate completely. A batch of arithmetic instructions followed in #334 (24-bit multiplies, bit fields, carries, sine and cosine, exponent and logarithm), each checked on the GPU. Since #343 a vertex shader's extra position outputs work too: in this game they always carry two clip distances, which the GPU uses to cut triangles off at a plane. With them, most of the game's vertex shaders translate completely. Texture sampling followed on 6 November (#433), with the rest of what the title screen needs (see below). On macOS the same translated shaders become Metal shaders through SPIRV-Cross; since #331 macOS CI converts every test shader and compiles it with Apple's Metal compiler. evill33t's Metal unit (#318, from #213) is the start of the Mac display.
  3. Engine draw hooks (working for the logos and title screen; begun in #335): route the game's render targets, clears, shader binding, textures and draws to the renderer, starting with the title screen's 2D passes. A first map found Sony's GPU helper library, compiled into the game, in one block of about 230 small functions: everything the game asks of the GPU passes through it, and the engine writes no GPU commands of its own. The library's draw functions and about 60 of its state setters are identified, along with the engine code that calls the draws. The game keeps its GPU state only in the commands those setters write, so the hooks will sit on the setters and draws themselves: each setter hands its value to the renderer, and each draw becomes a Vulkan or Metal draw. The library's key functions are identified (#341): its draw call, setRenderTarget, setViewport, the depth target and the user-data writers. Several are already decompiled in @evill33t's pull requests, as replacements verified to write exactly the original commands. The renderer will observe those replacements rather than change them. The shader files in the game's archive turned out to carry each shader's GPU register settings, and those settings were checked against the shaders' own code. They say where a shader's code lives, which inputs it gets, and what its extra outputs carry. On the runtime side, the renderer now keeps its own record of these calls for each command buffer (#342, #344, #345): render targets, viewports, shaders, their data and draws, ready to play back when the game submits the buffer. The next piece is the draw executor, which plays those calls back on a PC GPU. Its first step is done (#346, #348). Game shaders find memory by the PS4's addresses, so the runtime now keeps the game's GPU-visible memory at fixed places, and the translator adds one fixed offset to every address a shader forms. That lets the whole memory pool be handed to the GPU as a single buffer. A test on an RTX 3070 shows this works, at the cost of holding the 5 GiB pool in RAM while graphics run. Its second step works too (#368): given a written-down list of drawing calls, the executor runs them on a Vulkan GPU. It translates the shaders the calls name, finds or makes the picture they draw into, and draws. In a test with real PS4-style shaders, every pixel comes out right. Since #369 it is wired into the running game: with the display on, the calls run when the game submits its drawing work, and a flip shows what was drawn instead of a black frame. Until the game's drawing functions report their calls, nothing visible changes. Since #401 the record also keeps the GPU register values the game sets (blending, depth, primitive type, colour masks and the like), and the executor checks them before it draws: anything it cannot draw faithfully yet stops by name rather than drawing something wrong. Since 6 November the GPU library's decompiled replacements, by @evill33t (#411, from #233), report their calls to the renderer (#414), and a few library functions without replacements are observed where they are called (#416).
  4. Textures and 3D (begun): the texture formats and tiled layouts the title screen uses work (#427, #428, #441, #442). Meshes, materials and post-processing of the 3D game are still to come.

From black frames to the title screen

All of this was merged on 6 November 2026. Each step removed the next thing the boot stopped at by name; the renderer never draws something it cannot draw faithfully, it stops and says what is missing.

  1. Draw reports and hooks (#411, #412, #414, #415, #416): the GPU library's replacements tell the renderer which shaders are bound, the render targets, the shaders' data and each draw. setRenderTarget and the user-data writers are observed where they are called. Rectangle-list draws, which the game uses for full-screen passes, work.
  2. Compute (#418, #421, #424): the game's compute passes run on the GPU, including the ones that clear the screen and build its colour lookup tables. They read and write buffers in the formats their descriptors name, and images. A shader that needs something not translated yet stops the run by name while it runs.
  3. Pixel shaders (#425): a pixel's own screen position as an input, and the GPU's whole-quad mode.
  4. Textures and tiling (#427, #428, #432): the PS4 stores most images tiled, not row by row. The renderer knows the tiled layouts the game uses (linear, 1D and 2D thin), loads images from the game's memory in those layouts, and reads image descriptors the shaders load from memory.
  5. Sampling (#433): shaders read textures through the game's samplers (filtering and clamping). This gave the first frame that was not black: a flat grey from the game's colour-correction pass.
  6. Blending, depth and vertex fetch (#434, #435, #436, #437, #438): blending, depth and stencil targets, triangle strips, vertex shaders that call fetch shaders to read their vertices, and GPU state that carries over from one command buffer to the next.
  7. Indexed draws and the logos (#439, #440, #441): indexed draws, render targets that keep the game's memory up to date so later passes can read them, vertex colours and block-compressed (BC) textures. This drew the first logo, "Sony Computer Entertainment presents".
  8. Speed (#442): render targets are copied back to the game's memory only when something may read them, and unchanged images are not loaded again. In the maintainer's local runs a 90-second boot went from 66 frames to about 1,445, enough to reach the title screen at about frame 480. A shader reading data the game never set now stops by name. Draws still waited for the GPU one at a time. Since #463 (10 November) each submitted command buffer's draws and dispatches go to the GPU as one batch, and the CPU waits only where it reads what the batch produced; on the logos and title this alone changed nothing measurable: the limit there was the CPU's own tiling copies of the render targets. #472 moved those copies to a compute shader on the GPU, and in the maintainer's local runs the logos and title now run at the game's own 30 frames a second (about 14 before); the JAPAN Studio frame is still pixel-identical.

Roadmap

  1. Loader and boot harness: project-owned and independently tested.
  2. Kernel, threads, and memory: what start-up needs is in place: merged main boots through all eight milestones and keeps running, passing its GPU work through a temporary stand-in; no system call stops it (#408).
  3. Files, audio, network start-up: the game reads its own files read-only and keeps save data and trophies in a folder you choose; its sound is decoded and can play on your computer; its HTTP client and PSN calls answer offline.
  4. GNM and shaders: the logos and title screen draw natively in the maintainer's local runs (#441, #442). The renderer hooks the game's own drawing layer and translates its shaders, rather than emulating the GPU (see The renderer). In local runs with scripted input the menus after the title draw as well (#457, #471). Next: the rest of the first-run settings and character creation, then the 3D game's meshes, materials and post-processing, and overlapping the GPU's work with the next frame for speed (the logos and title already reach the game's 30 fps cap in local runs, #472).
  5. Movies and input: the game's movies decode with FFmpeg (#419, #420); a real controller and keyboard work with --input host (#431).
  6. Capture integration: add a return-aware, ABI-described observation boundary before connecting recordings to production hooks. Synthetic tests are not a substitute for real captures.

System-library work is tracked separately from boot milestones, in one issue per group: kernel (#34), files (#35), input and users (#36), audio (#37), video out (#38), GNM (#39), system services (#40) and network (#41). The network group now covers the byte-order and IPv4 helpers (both directions since #465), offline network control, the offline start-up and teardown of the network, SSL and HTTP libraries (#451), and the PSN identity, Plus and authorization checks of a signed-out console (#450, #461); sockets, resolvers and anything that would send data still stop by name. See Paleblood's runtime queue and runtime issues.

Network-group pull requests

Full-run dependency and replacement path

The current full-game path retains an external GPL-2.0-or-later scaffold and its required host, system-library, and graphics dependencies.

  • Paleblood's new hook callback covers only one host responsibility; it is not yet integrated into the full game-run path.
  • Paleblood's own pbboot harness builds and tests without that scaffold, but it does not yet provide equivalent full-game loading, services, rendering, or route checks.
  • The scaffold and its required attribution stay in the code repository until a project-owned replacement passes the same native game-run checks.
