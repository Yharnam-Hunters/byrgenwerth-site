Runtime

Paleblood is building a runtime of its own. A runtime is the software that loads a program and provides the system services it expects.

At a glance

Works

Stops at

The project has an ELF loader and boot harness that can load the game's executable and bundled system modules, bind imports, and run the entry point until it reaches a call the current runtime does not implement.

That is different from running the full game. Full native game runs still use a third-party host scaffold for the broader execution environment, system-library coverage, and Vulkan rendering. Paleblood supplies a project-owned hook plug-in and host interface, but the project-owned runtime has not replaced that host or passed equivalent full-run checks.

What works in Paleblood's runtime

ELF loading and boot diagnostics. runtime/loader.c maps the executable and bundled modules, applies relocations, and binds known imports. runtime/boot.c and tools/boot.py run the entry point and record how far it gets.

Selected system calls. The runtime supplies:

  • a small set of kernel/thread calls;
  • four libSceNet byte-order conversions;
  • an observed IPv4 text-to-binary conversion: sceNetInetPton implements the observed AF_INET path only;
  • four constrained offline libSceNetCtl behaviors: sceNetCtlGetState, sceNetCtlCheckCallback, sceNetCtlRegisterCallback, and sceNetCtlUnregisterCallback.

Together these are 9 of 175 imports in the network and online-services issue group. The runtime does not implement sockets, resolvers, HTTP, or online services. See runtime system-call notes and issue #41 for the group checklist.

Network calls that still fail loudly

For sceNetInetPton, other families and null-pointer error behavior remain fail-loud. The other imported NetCtl calls, sceNetCtlGetInfo and sceNetCtlGetNatInfo, remain fail-loud diagnostics because the PS4 information layouts and offline values are not established.

Function replacements and hooks. The project's plug-in receives the guest image and a hook-install callback, then registers its function replacements. Paleblood now also provides a small implementation of the version-1 hook callback:

  1. it checks the requested function range;
  2. it writes a jump to the replacement.

A synthetic executable-memory test confirms the patched entry reaches the replacement. The callback is not connected to the full game-run scaffold, and the test does not run the game.

What these merges do and do not show

After that saved run, contributor @EzequielRindello added guest-thread handle comparison in PR #62 and host-thread yielding through sched_yield in PR #72. Their registry tests check the implemented contracts; they do not demonstrate that a new startup path ran. The similarly named scePthreadYield remains an unresolved diagnostic because its PS4-visible return signature is not established. See Kernel for the evidence and limitations.

Merged PR #82 supplies imported memcpy and memset through the runtime symbol registry. PR #81 adds explicit thread-attribute detach-state setters with SCE and POSIX error conventions; reading a system-supplied default still fails loudly because its PS4 value is unknown. Their focused registry tests are synthetic evidence. Neither merge establishes a new boot result or changes verified game-function counts.

In the week of 26 October, @EzequielRindello added three more runtime services. PR #94 sleeps the host thread for sceKernelUsleep and usleep. PR #95 registers pthread_self, pthread_attr_init and pthread_attr_destroy under their POSIX names, alongside the SCE names. PR #97 ends the program by name when the game's stack protector calls __stack_chk_fail, which is that call's whole contract. Cases with no established PS4 answer still stop by name: usleep of a second or more, and any SCE error for sceKernelUsleep. None of these touches the current stop at scePthreadAttrGetaffinity, and the saved boot has not been rerun since they merged. See the runtime system-call notes for the evidence behind each.

Capture and replay

Paleblood has a local capture writer and replay verifier.

  • Saved cases carry function and run identifiers and use stable buffer ordering.
  • Replay checks reject a case for a different function or address.
  • The version-1 production hook interface does not observe function returns or describe pointer buffers, and current replacements do not call the recorder.

A separate test adapter proves that explicitly described synthetic inputs can be serialized and replayed. This checks the case format and verifier path only. It does not capture real game calls, prove a replacement against a real recording, or supply production run inputs. tools/promote.py consumes existing recorded cases and generated edge cases; it does not create captures.

The merged differential tools can now replay fixtures, observe supported guest instruction memory accesses, collect bounded control-flow coverage, minimize mismatches, and coordinate an opt-in candidate workflow. Unsupported instructions and skipped host-call bodies reject the trace; synthetic automation tests establish tool behavior only. The Architecture verification guide explains what is observed and which stages still require original-game evidence and human review.

Roadmap

  1. Loader and boot harness: project-owned and independently tested. The latest saved run of merged main 68d5f93 reaches the loaded milestone (0/8), before the executable's entry has completed.
  2. Kernel, threads, and memory: the present boot blocker. Issue #34 is contributor-claimed; preserve that ownership and run the harness after the relevant change merges.
  3. Capture integration: add a return-aware, ABI-described observation boundary before connecting recordings to production hooks. Synthetic tests are not a substitute for real captures.
  4. Files, input, audio, and video output: implement and measure each milestone as the boot harness reaches it.
  5. GNM and shaders: rebuild the game's graphics layer at its engine interface, then prove the first rendered frame.

System-library work is tracked separately from boot milestones. The network issue group has nine implemented imports: four byte-order conversions, the AF_INET path of sceNetInetPton, and four offline NetCtl behaviors. GetInfo and GetNatInfo remain callable unresolved diagnostics, as do sockets, resolvers, epoll, HTTP, and online services. The generated checklist reports 9/175 network-group imports implemented. See Paleblood's runtime queue and runtime issues.

Network-group pull requests

Merged PR #60 makes the registry and coverage tools preserve that distinction: unresolved diagnostics are excluded from implemented counts while still producing useful failure messages when called. Merged PR #63 adds the documented IPv4 text conversion for Bloodborne's observed AF_INET calls.

Full-run dependency and replacement path

The current full-game path retains an external GPL-2.0-or-later scaffold and its required host, system-library, and graphics dependencies.

  • Paleblood's new hook callback covers only one host responsibility; it is not yet integrated into the full game-run path.
  • Paleblood's own pbboot harness builds and tests without that scaffold, but it does not yet provide equivalent full-game loading, services, rendering, or route checks.
  • The scaffold and its required attribution stay in the code repository until a project-owned replacement passes the same native game-run checks.
