Runtime

Paleblood is building a runtime of its own. A runtime is the software that loads a program and provides the system services it expects.

The project has an ELF loader and boot harness that can load the game's executable and bundled system modules, bind imports, and run the entry point until it reaches a call the current runtime does not implement.

That is different from running the full game. Full native game runs still use a third-party host scaffold for the broader execution environment, system-library coverage, and Vulkan rendering. Paleblood supplies a project-owned hook plug-in and host interface, but the project-owned runtime has not replaced that host or passed equivalent full-run checks.

What works in Paleblood's runtime

ELF loading and boot diagnostics. runtime/loader.c maps the executable and bundled modules, applies relocations, and binds known imports. runtime/boot.c and tools/boot.py run the entry point and record how far it gets.

System calls. The runtime answers more than a hundred of the system calls the game imports: threads, locks and semaphores, memory, clocks, the console's start-up services, the network and HTTP libraries' offline start-up, sound output, and reading the game's own files. The runtime system-call notes explain each group, and end with a list of every call the runtime answers, generated from the code on every sync.

Where the PS4's behaviour is not established, the runtime does not guess: it stops and names the call. It plays no sound and draws nothing yet, and it never contacts a network.

Function replacements and hooks. The project's plug-in receives the guest image and a hook-install callback, then registers its function replacements. Paleblood now also provides a small implementation of the version-1 hook callback:

  1. it checks the requested function range;
  2. it writes a jump to the replacement.

A synthetic executable-memory test confirms the patched entry reaches the replacement. The callback is not connected to the full game-run scaffold, and the test does not run the game.

How far a boot gets

The table above comes from the last boot recorded on merged main. That boot still stops at scePthreadAttrGetaffinity, inside the game's bundled C library (see below).

To see what lies beyond that stop, the maintainer also runs local discovery boots that stand in for the two missing pieces (the affinity query and the reader-writer locks) without committing them. Such a run is not a merged-main result, but it shows which call comes next. On 30 October 2026 a local discovery boot:

  • started the game's threads, its HTTP client (offline) and its sound system;
  • found and read its first data file, sprj_mixer.fev, from the person's own copy;
  • stopped at the first graphics-driver call whose answer is not established (sceGnmValidateCommandBuffers).

Each call it passed through was then implemented and merged with its own evidence; the runtime system-call notes list them.

Capture and replay

Paleblood has a local capture writer and replay verifier.

  • Saved cases carry function and run identifiers and use stable buffer ordering.
  • Replay checks reject a case for a different function or address.
  • The version-1 production hook interface does not observe function returns or describe pointer buffers, and current replacements do not call the recorder.

A separate test adapter proves that explicitly described synthetic inputs can be serialized and replayed. This checks the case format and verifier path only. It does not capture real game calls, prove a replacement against a real recording, or supply production run inputs. tools/promote.py consumes existing recorded cases and generated edge cases; it does not create captures.

The merged differential tools can now replay fixtures, observe supported guest instruction memory accesses, collect bounded control-flow coverage, minimize mismatches, and coordinate an opt-in candidate workflow. Unsupported instructions and skipped host-call bodies reject the trace; synthetic automation tests establish tool behavior only. The Architecture verification guide explains what is observed and which stages still require original-game evidence and human review.

Compared with the 247/686 trace from PR #63, runtime changes merged since then, including module loading at run time (PR #83), raised the supplied-import count, but startup did not advance. The generated status above is synchronized from that run.

Why it is still the blocker. The call comes from the game's bundled C library, not from the executable, and its answer for the main thread is not established. BluePinetree has claimed the work that lets the runtime replace a function inside a bundled module, so this query can be answered there. Until that lands, merged main stops here.

Boot history fields (PR #51)

PR #51 extended new symbols/boot_history.csv rows with the run outcome, execution phase, unresolved-import return site, and guest-fault location, signal, and address. A changed failure location is recorded even when import counts and the blocking symbol stay the same. Existing rows remain readable.

After relevant changes merge, compare the history fields added by PR #51 against the saved failure location and trace.

Roadmap

  1. Loader and boot harness: project-owned and independently tested.
  2. Kernel, threads, and memory: most of what start-up needs is in place. Merged main still stops at scePthreadAttrGetaffinity until BluePinetree's module replacement lands.
  3. Files, audio, network start-up: begun. The game reads its own files read-only, its audio thread runs in real time without sound, and its HTTP client starts offline.
  4. GNM and shaders: begun. The game builds its GPU commands itself and only submits them, so the graphics are rebuilt in the engine's own renderer (its GX framework), not by emulating the GPU; the goal is the first rendered frame. Mapping that renderer is the next step.
  5. Capture integration: add a return-aware, ABI-described observation boundary before connecting recordings to production hooks. Synthetic tests are not a substitute for real captures.

System-library work is tracked separately from boot milestones, in one issue per group: kernel (#34), files (#35), input and users (#36), audio (#37), video out (#38), GNM (#39), system services (#40) and network (#41). The network group now covers the byte-order and IPv4 helpers, offline network control, and the offline start-up of the network, SSL and HTTP libraries; sockets, resolvers and anything that would send data still stop by name. See Paleblood's runtime queue and runtime issues.

Network-group pull requests

Merged PR #60 makes the registry and coverage tools preserve that distinction: unresolved diagnostics are excluded from implemented counts while still producing useful failure messages when called. Merged PR #63 adds the documented IPv4 text conversion for Bloodborne's observed AF_INET calls.

Full-run dependency and replacement path

The current full-game path retains an external GPL-2.0-or-later scaffold and its required host, system-library, and graphics dependencies.

  • Paleblood's new hook callback covers only one host responsibility; it is not yet integrated into the full game-run path.
  • Paleblood's own pbboot harness builds and tests without that scaffold, but it does not yet provide equivalent full-game loading, services, rendering, or route checks.
  • The scaffold and its required attribution stay in the code repository until a project-owned replacement passes the same native game-run checks.
