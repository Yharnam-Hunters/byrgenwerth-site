Function families

Tens of thousands of the game's functions are copies of the same code: most are a few bytes long, and some are larger functions the compiler emitted again at hundreds of addresses. A family replaces each such shape once, with one readable body, and proves it on every copy. Families move the function count far more than the byte count, so this page always shows both.

At a glance

What
Empty methods, functions that return 0 or a fixed number, getters and setters of one field, record initializers, and since 16 November larger copies such as deleting destructors and static initializers: each family is one shape, and every function with exactly that shape is a member.
Proof
Every member runs its edge cases on the original and on the replacement, compared as strictly as any hand-written function, and deliberately wrong versions must fail. Since 12 November members are also verified by byte-exact matching: each member compiles byte for byte from the family's own source, and an independent family review approves it (#688, #691, #703, #725). The first nineteen families are verified this way; the families added since 15 November are edge-verified, and 23 of them have byte-exact matching records waiting for their family reviews (#1165).
Honest numbers
Members are a large share of the functions but a very small share of the code's bytes (the table below). Most of the game's code is still ahead.
Source
Paleblood's docs/FAMILIES.md, merged in #515, #527, #529 and #531 (10 November 2026), with relative shapes from #1099 (16 November).

Why the executable is full of tiny functions

C++ code is full of small virtual methods and accessors. When a class overrides a method to do nothing, the compiler still emits a function for it: a lone ret. A getter that returns a pointer kept some way into an object becomes mov rax, [rdi+K]; ret, where rdi holds the object and K is where the field sits. The compiler emits these bodies again for every class, so the executable holds thousands of identical copies. Each is a real function in the export, so each counts in the function total, but each is only one to a few bytes long.

Writing and proving each copy by hand would be pointless work, and leaving them out would leave the game's call graph full of unreplaced leaves. A family does them all at once.

What makes a function a member

A family is defined by its exact bytes, with at most one parameter (the field offset, or the constant returned). Since #1108 the field offset may also be a 32-bit one, for fields further than 0x80 bytes into an object. Paleblood's tools/family_scan.py reads your own copy of the executable and takes a function only when:

  • its bytes are exactly the family's shape, from its start to its exported end;
  • everything after it up to the next function is the compiler's padding, and there is enough room for the hook's 14-byte jump, so installing the replacement overwrites only padding and never the next function (see Ghidra & PS4 Quirks);
  • nothing patches it: no relocation, no community frame-rate patch line, no other replacement or observation hook names it.

Shapes are kept deliberately narrow. A body that reads a global, calls a fixed function, or writes only part of a register (which would keep the caller's upper bytes) is not an exact-byte family: no synthetic case could stand in for the value it depends on. Calls through the object's own table of virtual functions are allowed, because the case builds that table itself (#1135).

Larger copies: relative shapes

Some larger functions were also emitted at many addresses: an inline function's guarded static initializer, or a deleting destructor that calls the same destructor and then operator delete. Their copies are the same code, but because each sits at a different address, the distances in their calls and global reads differ, so their bytes are not identical. #1099, by @FFwLo, lets a family's shape say "here is a distance that must reach this exact global or function". A copy is a member only when every other byte matches and every such distance, measured from the copy's own address, reaches the same target, so every member is the same code using the same globals and functions. Its cases then control those globals and stub those calls, just as for a hand-written replacement. A relative shape may also carry one parameter (a class size, an event kind) since #1138. Members of a relative family are as long as the function they copy, so unlike the tiny families they are large enough for the recorder's hook and can reach verified through in-game recordings.

The member count and bytes are written down before the member table is generated, and the generator refuses a table that differs, so a family cannot quietly grow.

How a family is proved

Every member runs its edge cases on the original machine code and on the replacement, with registers and memory compared exactly as for a single hand-written function. The cases seed the return register and the argument registers with values no replacement could guess, point every argument at a probe buffer, and compare all writable memory afterwards. On a sample of members, at least one per parameter value, every listed wrong version (a mutant) must fail, and for a parameterized family so must the replacement for a neighbouring value. A run with any failure or surviving mutant records nothing.

Members become verified the way any function does: a current edge result, current in-game recordings or a current byte-exact match with every reference checked, and an approved independent review. Recordings cannot reach most members: the recorder's hook needs room to move a function's first instructions, and a member is one to six bytes followed by padding. So members take the matching path: tools/match.py family compares every member with the family's generated matching source and records the result per member, the family's independent review approves each member, and tools/promote.py --families moves each member with all three to verified (#688). On 12 November that verified 4,426 field getters and setters (#691), 3,777 constant getters and member addresses (#703) and 9,816 empty, zero and identity functions (#725).

The copy counts are the ones each PR states. What many of these copies belong to (which class, which table) is not known from their code alone, so several families are named after what they do or the address they reach.

Matching records for the new families

#1165, by @FFwLo, adds byte-exact matching records for 23 of the new leaf families (1,538 copies): each member compiles to its exact bytes from the family's generated source with the original compiler and flags, with every reference checked. Six other families with matching templates do not compile exactly yet and have no record. The records change no status: each member still needs its family's independent review before it can be promoted to verified. Relative families have no matching template; they take the recorded path instead.

What the families do not tell you

  • How much of the game is done. Read the bytes column: the shapes are tiny, so even every member together is a small fraction of the code. The real work, the long functions that hold the game's logic, is unchanged by them.
  • What each member is for. A getter at offset K is the same bytes in every class that has a field there; which class and which field each member belongs to is not known from the bytes. Names come later, from the code that calls them.
