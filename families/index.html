Function families

Tens of thousands of the game's functions are tiny copies of the same few bytes. A family replaces each such shape once, with one readable body, and proves it on every copy. Families move the function count far more than the byte count, so this page always shows both.

At a glance

What
Empty methods, functions that return 0 or a fixed number, getters and setters of one field: each family is one exact byte shape, and every function with exactly that shape is a member.
Proof
Every member runs its edge cases on the original and on the replacement, compared as strictly as any hand-written function, and deliberately wrong versions must fail. Since 12 November members are also verified by byte-exact matching: each member compiles byte for byte from the family's own source, and an independent family review approves it (#688, #691, #703, #725).
Honest numbers
Members are a large share of the functions but a very small share of the code's bytes (the table below). Most of the game's code is still ahead.
Source
Paleblood's docs/FAMILIES.md, merged in #515, #527, #529 and #531 (10 November 2026).

Why the executable is full of tiny functions

C++ code is full of small virtual methods and accessors. When a class overrides a method to do nothing, the compiler still emits a function for it: a lone ret. A getter that returns a pointer kept some way into an object becomes mov rax, [rdi+K]; ret, where rdi holds the object and K is where the field sits. The compiler emits these bodies again for every class, so the executable holds thousands of identical copies. Each is a real function in the export, so each counts in the function total, but each is only one to a few bytes long.

Writing and proving each copy by hand would be pointless work, and leaving them out would leave the game's call graph full of unreplaced leaves. A family does them all at once.

What makes a function a member

A family is defined by its exact bytes, with at most one parameter (the field offset, or the constant returned). Paleblood's tools/family_scan.py reads your own copy of the executable and takes a function only when:

  • its bytes are exactly the family's shape, from its start to its exported end;
  • everything after it up to the next function is the compiler's padding, and there is enough room for the hook's 14-byte jump, so installing the replacement overwrites only padding and never the next function (see Ghidra & PS4 Quirks);
  • nothing patches it: no relocation, no community frame-rate patch line, no other replacement or observation hook names it.

Shapes are kept deliberately narrow. A body that reads a global, calls anything, or writes only part of a register (which would keep the caller's upper bytes) is not a family: no synthetic case could stand in for the value it depends on.

The member count and bytes are written down before the member table is generated, and the generator refuses a table that differs, so a family cannot quietly grow.

How a family is proved

Every member runs its edge cases on the original machine code and on the replacement, with registers and memory compared exactly as for a single hand-written function. The cases seed the return register and the argument registers with values no replacement could guess, point every argument at a probe buffer, and compare all writable memory afterwards. On a sample of members, at least one per parameter value, every listed wrong version (a mutant) must fail, and for a parameterized family so must the replacement for a neighbouring value. A run with any failure or surviving mutant records nothing.

Members become verified the way any function does: a current edge result, current in-game recordings or a current byte-exact match with every reference checked, and an approved independent review. Recordings cannot reach most members: the recorder's hook needs room to move a function's first instructions, and a member is one to six bytes followed by padding. So members take the matching path: tools/match.py family compares every member with the family's generated matching source and records the result per member, the family's independent review approves each member, and tools/promote.py --families moves each member with all three to verified (#688). On 12 November that verified 4,426 field getters and setters (#691), 3,777 constant getters and member addresses (#703) and 9,816 empty, zero and identity functions (#725).

What the families do not tell you

  • How much of the game is done. Read the bytes column: the shapes are tiny, so even every member together is a small fraction of the code. The real work, the long functions that hold the game's logic, is unchanged by them.
  • What each member is for. A getter at offset K is the same bytes in every class that has a field there; which class and which field each member belongs to is not known from the bytes. Names come later, from the code that calls them.
