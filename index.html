Paleblood is a decompilation of Bloodborne with its own runtime, one verified function at a time

We are born of the blood, made men by the blood, undone by the blood. Our eyes are yet to open… Fear the old blood.Master Willem / The Blood Minister

Paleblood rewrites Bloodborne (PS4, CUSA03173, version 1.09) function by function as readable C++ that does exactly what the original did, and builds a runtime of its own for that code to run on.

Where the hunt stands

The game doesn't run on Paleblood yet: 21 of 157,757 functions are verified (0.01%). On our own runtime the executable's boot gets as far as scePthreadAttrGetaffinity (libkernel, called by libc.elf), with 252 of 686 system imports provided.

More about the project

Why we do this, and the goal

Because we love this game. Yharnam deserves to outlive the hardware it was made for, and to be understood as well as it is loved: every function of the original, read, named, rewritten and proved to behave exactly as it did, so that one day it runs natively, at any frame rate, for as long as there are hunters to play it.

The goal is a complete source port of Bloodborne for the PC. When the hunt is over, every function of the game's 1.09 executable will have been rewritten as readable C++ and proved to behave exactly like the original, and the game will run natively on Paleblood's own runtime: no PS4, no emulator, no original executable, only the game's data from your own copy. Because it will be source, the game can be read, understood, preserved, fixed and modded like any other program, at any frame rate and resolution.

Two tracks get there, side by side:

  • Decompilation: functions rewritten as readable C++ and proved against the original in the verification harness, on inputs recorded earlier and on generated edge cases.
  • Runtime: our own loader (done), input capture (a game run can now record a function's inputs by tracing the original), kernel, threads and memory, files, input, audio, video out, and the graphics, rebuilt at the engine's own level rather than by emulating the PS4's GPU (Runtime).

The game does not run on Paleblood until the runtime is far enough along that road. Today the harness maps the executable and bundled modules, then stops during bundled libc startup at an unresolved system import, before the first boot milestone; full game runs still use an external host scaffold while the project-owned runtime is completed. Past that stop, the runtime already answers the calls the game makes to start its threads, sound and file reading; the Runtime page shows how far a boot gets.

How a function becomes verified

  1. Analyze. Ghidra with the GhidraOrbis loader finds the function in your own dump; its callers, callees and the memory it touches are read from the disassembly, not only the decompiler.
  2. Name. It gets a name and a system in the shared function table, so every contributor's Ghidra shows the same names.
  3. Rewrite. A readable C++ version: named structures instead of raw offsets, named calls instead of addresses, named constants, faithful to what the original does.
  4. Verify. The harness runs the original and the replacement on equivalent recorded and generated inputs, comparing ABI-selected results, preserved registers, declared memory state, and scripted library calls. Optional instruction tracing adds bounded access and control-flow observations; its limits are described in Architecture. Deliberately wrong versions must fail.
  5. Review. An independent reviewer checks the verification and the readability. A function whose code no recording reaches yet is edge-verified until one does.
