Engine

The engine's shared plumbing that every system leans on: its fatal error report, its check for missing singletons, its reference-counted objects, and small helpers such as writing a line to the standard error stream.

At a glance

Engine-wide helpers in Paleblood's game/engine/: the fatal error report and singleton check, reference counting, and replaced engine utility functions.
Verified

Summary

What every system shares

Most replaced functions lean on a few engine-wide pieces:

  • The fatal error report (0x024b55b0) takes a source file, a line and a message. In the shipped game it logs and returns, so the code after it keeps running; Ghidra wrongly treats it as never returning (see Ghidra & PS4 Quirks).
  • The singleton check. Many systems are singletons (FrpgNetMan, SprjEventFlagMan, ...). Code that needs one reports it by name through the fatal error report when it is missing, then reads it again and uses whatever is there.
  • Reference-counted objects (DLReferenceCountObject). An object counts its holders; dropping the last reference destroys it through its first virtual function, and dropping one more than it has is reported as an invalid unref. The render frame update and the Chalice Dungeon gate's handle share this code (#185).

Writing to standard error

engine_write_stderr (0x0111a740) writes a text to the standard error stream: it reads the C library's stderr once, passes the text to fputs, ignores the result, and returns 0.

How the stderr writer was verified

By @evill33t in #113, brought up to date with main and merged in #205. Its 28 constructed edge cases pass against the original on current main, and an independent review approved it; no frame-rate patch edits it. It has not been checked on frames recorded from a real game run.

Comparing strings

Two byte-string comparisons compare signed bytes and return the difference at the first mismatch: engine_compare_signed_strings (0x011c4970) runs to the end of the strings, and engine_compare_signed_prefix (0x011c4990) stops after a length, still comparing the first byte when the length is zero or negative. All their callers are in FMOD's code (see Audio).

More string helpers

Since 4 November the engine's small C-string helpers are mapped too, by @evill33t: engine_string_length (0x011c47f0, a strlen whose result is cut to 32 bits, #288), engine_ascii_to_upper_in_place and engine_ascii_to_lower_in_place (0x011c4910, 0x011c4940: change letters in place and return the string, #281), and engine_compare_ascii_ignoring_case (0x011c49c0, compares two strings ignoring letter case, #282).

Three more followed on 5 and 6 November, also by @evill33t:

  • engine_string_append (0x011c4870) appends one zero-terminated string to another, a strcat that returns the destination (#337, from #118);
  • engine_string_append_counted (0x011c48b0) appends at most a given number of bytes, counting only the low 32 bits of the count, and ends the result with a zero; a count of zero touches neither string (#337);
  • engine_ascii_to_lower (0x011c48f0) lowercases a single character: it changes A-Z to a-z, leaves every other byte as it is, and returns the byte as a signed 32-bit value (#125).

Wide strings and owned storage

  • engine_wide_string_destroy (0x02a44140) releases a wide (16-bit character) string, and engine_initialize_static_wide_string_0217ffb0 sets up one static wide string the first time it is needed, guarded so it happens once (#284).
  • engine_release_owner_storage and engine_resize_owner_storage (0x0132c590, 0x0132c6c0) free an object's storage block through its allocator, or replace it with a new 16-byte-aligned block of the requested size (#285). What kind of object owns the block is not known yet; its only known caller is 0x02713870.

Storing a word and a product

engine_store_word_product (0x011c4510) stores two 32-bit fields of an object: one input as it is at offset 0x18, and the product of two other inputs times four at offset 0x1c, then returns 0 (#336, from #115 by @evill33t). What the two fields mean is not known yet; it is called from 0x01111bb0 and through slot 1 of the function table at 0x0500ae48.

Looking up a table entry by handle

engine_entry_manager_resolve (0x01314320) turns a handle into an entry: it checks that the table is enabled, rejects the all-ones handle, uses the handle's low 32 bits as an index checked against the table's capacity, and rejects an empty entry. Its callers are a family of functions at 0x02717f30-0x02718c80 and 0x0210f5a0; what the table holds is not known yet.

How these were verified

By @evill33t: the comparisons in #107, merged in #274 (18 and 24 cases), and the lookup in #110, merged in #276 (25 cases). Each was brought up to date with main, its constructed edge cases pass against the original on current main, and an independent review approved it. The appends (#337, 32 and 48 cases), the word-and-product store (#336, 32 cases) and the single-character lowercase (#125, 291 generated cases) are edge-verified: their constructed cases pass against the original. None was checked on recorded game runs.

Memory: the engine's heaps

The engine (FromSoftware's Dantelion2 library) never asks the system for memory one object at a time. It carves a few large ranges into heaps, each with its own strategy, and every system allocates from one of them. On 12 and 13 November the heaps' allocation, free, set-up and diagnostic paths were replaced, function by function, each with its own edge-case generator that builds heaps of known shape:

  • The robust heap (DLRobustHeap): 31 small-size free lists plus a red-black tree of larger free blocks. It allocates by best fit from the bottom or by the highest-addressed fit from the top, aligned or not, and its free reports a double free or an address outside the heap through the engine's error report, then frees the block anyway, as the game does (#667, #670, #708, #721).
  • The regular heap (DLRegularHeap): 64 size lists; its free was the most called heap function in a coverage boot to character creation (#675, #708, #721). A locked variant guards it with a mutex, and the heap manager keeps every heap's range in an array sorted by start under a read-write lock (#758, by @FFwLo).
  • The segregated heaps (DLSegregatedBiHeap, DLSegregatedRegularHeap): the block descriptors live outside the memory they manage, handed out by a fixed-size allocator (DLFixedAllocator); the bi-heap allocates from both ends and checks its own consistency before reporting a bad free (#677, #680, #690, #717).
  • Small objects and per-thread memory: the small object allocators and their fast variants, the per-thread temporary heap (well over a hundred functions create it on entry) and the linear heap, used from both ends (#721, #803).
  • The user interface's heap: identified as Scaleform 4's page-table heap from its page signature, with bins of free blocks and a two-bits-per-unit page bitset; its allocation, aligned allocation, reallocation in place and free are replaced (#699, #732).

The same work replaced the engine's thread helpers, condition signals and semaphores (#803; the engine's mutex wrappers are on the Kernel page) and, by @FFwLo, the wide string's assign from part of another string and its growth (#737).

Vector and rotation math

The wind update of #568 (see Render) inlines the engine's four-lane vector math, now in game/engine/rotation_math.h: a sine and cosine polynomial evaluated on four values at once, a rotation quaternion built from half-angles, the rotation matrix made from it, and a vector length refined with a Newton step. vector_operations.h gained additions and multiplications that keep the original's operand order, so NaN results carry the same payloads. They are helpers of that replacement, not separate functions of the executable.
