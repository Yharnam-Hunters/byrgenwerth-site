Render

The render system draws each frame and presents it to the screen. This page covers the per-frame render update, the pacing of each present, one helper from the YEBIS post-processing middleware, and the GPU helper library compiled into the game: its command writers, state setters, swap chain and shader uploads, and how they now report to Paleblood's renderer.

At a glance

Scope
render_frame_update_02377bd0, render_swap_chain_present, render_yebis_get_recursive_sample_parameters, and the GPU helper library's command writers, state setters, swap chain and shader uploads.
Verified
All three: the reference-counted object list, the vblank pacing of the present, and the blur sample counts.
Open
What the listed objects and the two children are; the engine's own drawing code above the GPU library, materials and post-processing. Many GPU library functions are mapped and edge-verified; they now tell Paleblood's renderer what they set.

Summary

The per-frame update

render_frame_update_02377bd0 (0x02377bd0) runs once a frame:

  1. It walks a list of reference-counted objects and updates each one.
  2. An object whose update says it is finished loses its reference (destroyed at the last one; an underflow is reported as "DLReferenceCountObject: Invalid Unref() call"), and its node is unlinked and freed.
  3. It updates a RendMan-side child (RendMan: singleton 0x05940298).
  4. It steps another child by a frame time of 1/30 s, or 0 while that child is held.

Pacing the present

render_swap_chain_present (0x025b2fb0, the graphics framework's GXSwapChainCtrl) paces each present:

  1. It waits until the requested number of 60 Hz vblanks has passed since the last present. It sleeps until 17 ms before that time, then polls the clock.
  2. It maps the interval to a flip mode.
  3. It presents.

In Iosefka's Clinic the game presents with interval 1 and does not wait here; the frame limiter sets the pace.

Blur sampling (YEBIS)

render_yebis_get_recursive_sample_parameters (0x00fbc3e0) belongs to YEBIS, the post-processing middleware. Its GPUTexUtil_GetRecursiveSampleParameters works out:

  • how many recursive passes a blur needs;
  • how many samples the last one takes;
  • how far apart the first one samples.

It carries the middleware's own assertions.

Scope still to map: the engine's draw submission above the GPU library, materials and post-processing.

The game's shaders ship as compiled AMD GPU code in its shader bundles. A census tool in the code repository decodes the shaders in your own copy and counts the instructions they use, for Paleblood's shader translator (Paleblood #316). It prints counts only; no shader code leaves your machine.

Writing GPU commands and presenting

The engine builds the GPU's command buffers itself (see Runtime syscalls), as AMD "PM4" packets: each packet is a header word naming the operation, followed by its arguments. The first of the engine's own packet writers are mapped, all by @evill33t:

  • The command buffer. One shared structure describes it: where it begins and ends, the cursor where the next word goes, and a callback the engine calls to get more room when it runs out. render_command_prepare_submission (0x014784a0) reserves 64 words before a submission, and render_command_emit_counter_operation (0x01477b30) writes a seven-word packet that makes the GPU wait on a value in memory (PM4 WAIT_REG_MEM) (#208).
  • The pool counter. render_read_present_pool_counter (0x0247eb80) reads a 64-bit counter atomically, with a locked compare-and-exchange loop (#279).
  • Present records. render_present_record_consume (0x02ab5a70) turns a pending present record into commands: it classifies the record, clamps its range, copies its payload and writes the final fields (#286).
  • Building present records. render_build_present_source_record (0x0256e1d0) builds the record for a present, by mode, keeping partial output, unsigned divisions and the packed auxiliary requirements as the original does; render_choose_record_constructor_selector (0x02ab7a20), render_combine_record_parameters (0x02ab7ab0) and render_reduce_record_parameter (0x02ab7e40, a four-entry scale table, zero past its end) pick and combine its constructor choices (#473, from #268; edge-verified on synthetic cases).
  • A record test. render_record_auxiliary_predicate (0x02abb4f0) answers yes or no for a record's selector: always yes for two selector values, a flag bit for the next two, no otherwise (#293, from #266).
  • Presenting a swap-chain image. render_swap_chain_present_mode (0x02ad5dd0) waits until the display has flipped far enough and picks the flip mode, and render_swap_chain_submit (0x02ad6e50) submits the frame, advances the frame counter and checks its owner again (#287). They use the public layouts of the video-out flip status and kernel events.
  • Depth and stencil clears. render_emit_present_preparation_scalar (0x01473590) and render_emit_present_preparation_byte (0x014735f0) write the depth and stencil clear values (AMD's DB_DEPTH_CLEAR and DB_STENCIL_CLEAR registers) #325, from #210.
  • The last record's depth settings. render_emit_present_last_record_packet (0x014769e0) writes DB_RENDER_CONTROL. Two setters turn its depth and stencil compression off or on (0x01485070, 0x01485080), one replaces two packed indices (0x014721d0), and render_reset_present_preparation_dirty (0x02ad2c30) writes only the clear values that changed and remembers them #326, from #211.
  • Resource records. A record describes a GPU resource's layout. The reviews tie its fields to AMD's public tiling and format fields, though the full meaning is still open. The mapped parts:
  • mapping: render_pack_record_mapping_word (0x01471310) packs its mapping word and render_read_record_mapping_word (0x01486cf0) reads one back #321, from #212;
  • encoding: three lookups decode the encoding byte's metadata, component arrangement and category (0x01471730, 0x014717a0, 0x014719a0), and render_record_set_encoding (0x01486540) stores it #327, from #261;
  • parameters: render_record_apply_parameter_tuple (0x0149c850) picks a record parameter from a normalisation table, with its classification helpers (0x0149e900–0x0149ea70) #322, from #223;
  • sizes: render_calculate_second_auxiliary (0x0149e570) works out the size and alignment of a second auxiliary area #323, from #228;
  • fields: seven setters (0x01486520–0x01486800) replace one field each, keeping the rest of the word #324, from #236;
  • construction: render_record_constructor (0x01485f90) clears a record's 44-byte prefix and fills in the record and its auxiliary outputs, returning a packed 64-bit result; render_record_constructor_pack_pair (0x01471600) packs a selector pair into an encoding, and two optional steps (0x0149e2d0, 0x0149e400) align paired components and work out the geometry, writing their outputs even when a helper reports an error #478, from #246 (edge-verified on synthetic cases);
  • normalisation: render_record_normalize_mode2, …mode3 and …mode4 (0x025710a0, 0x025711d0, 0x02571340) bring a record's input into one normalised form, copying the words they do not interpret unchanged and keeping each helper's writes and failure codes in order, and render_record_translate_selector (0x02ab7310) maps a record selector to one output word, answering status 12 for a selector it does not support #249 (edge-verified on synthetic cases).

Setting GPU state and drawing

The GPU helper library keeps no state of its own: each setter writes its value straight into the command buffer as a register packet, and the GPU reads it from there. A large group of setters and draw writers was mapped and replaced by @evill33t, each verified to write exactly the original packets:

  • Blending and colour output #411 (from #233): render_set_cb_blend_control (0x01473090, one colour buffer's blend equation, CB_BLENDn_CONTROL), render_set_cb_color_control (0x01473320, the colour output mode and raster operation, CB_COLOR_CONTROL) and render_set_cb_target_mask (0x01472fd0, which colour components each target writes, CB_TARGET_MASK).
  • Depth and stencil #411: render_set_db_depth_control (0x014733a0, the depth and stencil tests and writes) and render_set_db_stencil_control (0x01473400, the front- and back-face stencil operations).
  • What is drawn #411: render_set_vgt_primitive_type (0x01473fe0, triangles, strips, rectangles and so on), render_emit_num_instances (0x01475370, how many copies a draw makes), render_emit_draw_index_auto (0x014741b0, a draw of consecutive vertices) and render_emit_event_write (0x01475da0, a GPU event such as a cache flush), with two record helpers (0x01485390, 0x014853f0) and the one call that asks the system whether the GPU's performance-analysis mode is on (0x01489c40).
  • Where on screen #364 (from #232): render_configure_viewport (0x014765e0, the viewport's scale, offset and depth range), render_configure_screen_scissor (0x01476790), render_set_screen_offset (0x01473650), the guard-band clip and discard adjustments (0x014736d0, 0x01473750) and the viewport-transform controls (0x01476980, 0x01485220).
  • A present's context section #365 (from #231): render_emit_present_context_section (0x01472870) reserves room and writes the context registers a present needs.

Command buffers, swap chain and shader uploads

  • Command buffers #360 (from #256): render_command_buffer_init (0x01471270) sets up a command buffer's pointers and its "need more room" callback. render_command_submit_batch (0x02ab0ce0), render_command_submit_snapshot (0x02ab0e30) and render_command_submit_present (0x02aafb30) hand finished regions to the system's submit call, with the waits the GPU needs. The room check that every packet writer makes before writing is now shared code #291.
  • The swap chain #361 (from #254): render_setup_swap_chain (0x02ad5e90) allocates and registers the swap chain's frame buffers with video out and sets up its cached resource data and tone curves; two cleanups release the curve and the cached record (0x02571c60, 0x02572290, #359, from #244).
  • The last present record #354 (from #260): render_present_last_record_consume (0x02ab6810) consumes the final record of a present, or only updates its tracking when the commands do not fit.
  • Shaders #263, #363 (from #251): render_flush_shader_preparation (0x02ab9850) flushes a pending barrier before a shader event, and render_allocate_shader_upload (0x02aaddc0) finds room of at most 64 KiB for a shader's code, reclaiming once if none is free.
  • Resource descriptors #357 (from #255), #358 (from #222): the records that describe a texture's layout, its mip levels and their offsets (0x014a1e80, 0x014a2c40), its encoding (0x014712d0, 0x01471770, 0x01489910-0x01489960) and its tiling (0x0149cc60, which converts a tile-mode table index), and how its parameters are derived (0x02abaf10, 0x0149cb30).

Render targets, descriptors and the present path (10 November)

Forty-five more of the library's functions were replaced on 10 November, all @evill33t's work, brought up to date with main and merged as #482, #485, #486, #487 and the batch #489:

  • Render targets #489: render_set_render_target (0x014738b0) writes a colour target's register block, or switches the target off when there is no descriptor; render_set_depth_render_target (0x014739b0) does the same for the depth target. render_restore_color_target_from_bank and render_restore_depth_target_from_bank (0x02ad1e30, 0x02ad1e70) put a saved target back from one of two banks, and render_present_slot_emit (0x01473840) writes a colour target's two clear words.
  • Rasterizer state #489: render_configure_viewport_and_guard_band (0x01496f60) sets the viewport and the guard band, the region outside the screen where triangles are kept rather than clipped; render_set_pa_sc_mode_cntl_0 (0x01477150) switches multisampling and the viewport scissor.
  • Linking shaders #489: render_build_shader_link_words (0x014873a0) matches a vertex shader's outputs to a pixel shader's inputs and builds the words that connect them; render_emit_shader_link_words (0x01475000) writes them. render_configure_record_shader, its secondary path and render_finish_record_shader (0x02ace1e0, 0x02ace5e0, 0x02acfc20) set up and finish a recorded shader's state.
  • Descriptor geometry #482, #485, #486, #489 (from #237, #247, #238): building a resource descriptor and the requirements it adds up (render_prepare_resource_descriptor, 0x02fa6af0), the two- and three-part record descriptors and their size (0x01487ee0, 0x01488590, 0x01488370, 0x014a27c0, 0x01471a40), converting a constructor's record (0x01488d90), and render_record_geometry (0x0149ce10) with its helpers (0x0149c4e0-0x0149ed30), which work out an image's dimensions and alignment for the record constructor.
  • The swap chain's resources #487, #489 (from #245): render_initialize_swap_chain_resource (0x02565f90) checks a frame buffer's parameters, prepares its storage and wraps it; render_prepare_swap_chain_resource_info (0x02571d60) allocates that storage and publishes its descriptor.
  • Finishing a present #489: the chain that closes a frame's command lists and hands them on. render_finish_present_commands (0x02aaf700) finishes pending lists and submits the pending snapshot when there is room (render_submit_present_finish_snapshot, 0x02ab0b00; render_managed_present_capacity, 0x02aaf030); a pool of present buffers is claimed and released (0x02ad3b80, 0x02ad3c80, 0x02ad3d40, 0x02aaa5a0); the release packets that tell the GPU a buffer may be reused are written (0x014778f0, 0x02abb6d0); and the present's sources are prepared and their state flushed (0x02ad1eb0, 0x02ad1f80), with the encoding helpers 0x02564ed0 and 0x02565130 and the context finisher 0x02568530.
  • Resetting a present's context #557 (from #257, 11 November): five finishers put a present's context back to its starting state. render_reset_present_context_preparation (0x02ad2d20) resets both nine-entry banks of preparation records and the state around them; render_prepare_present_context_scratch (0x02ad3070) prepares the live bank's changed records before the present finishes, reloading the bank on every pass; render_reset_present_context_shader_state (0x02acd190) clears the conditional-command flag and refills the shader state, keeping the invalid-value markers between fills; and two small resets (0x02abba10, 0x02ad3300) set one embedded state block to zero and that marker, leaving padding and a shared scalar's bits as they were. What each bank's records stand for is still open.

Wind on models

render_update_model_wind (0x02713870) gives each model its wind, which the grass and tree shaders read as WindForceAndTime and PointWindForce. Every model draw calls it (0x0216f9d0, 0x02124660). For the model's wind receiver it:

  1. ages the influences it keeps: each fades out over its last 0.75 s while its wave time advances by the wind step;
  2. copies the live influences, up to four in each of two lists, to the output;
  3. samples every attached wind source: a base speed, a gust from fractal noise, and a direction turned by noisy angles;
  4. adds or refreshes that source's influence, ramping it in over 0.1 s. Kinds 0 and 3 go to the first list, which keeps the strongest four once full.

It was the last function on the list of frame-rate-patched functions in issue #32, now closed (#568, 11 November). The patches point its three 1/30 s step loads at their own frame-time cell and rewrite one to use the measured frame time; BB_TARGET_FPS does the same in code (see The frame limiter). Three quirks of the original are kept: three stale stack bytes copied into every influence, a failed lookup keeping the previous source's jitter, gust and cycle values, and a hold flag that zeroes the step for every later source. What each source kind stands for is still open.

How the wind update was verified

Edge-verified: 120 constructed cases pass against the original stock and with the pinned community patch file for 30 FPS++, 60 FPS++ and Uncap FPS++ (each run with the matching BB_TARGET_FPS); 109 of the original's 125 branches were seen both ways, and every non-equivalent one of 70 deliberate mutants fails in at least one mode. A separate review session that did not write the code requested changes, then approved the fixes. It becomes verified once recordings from the game exist.

More GPU library replacements (13 November)

Contributor @FFwLo replaced functions that earlier replacements still called as originals, all edge-verified: three shader packet writers, among them the pixel shader setter (#769); the two cache-coherence packets (ACQUIRE_MEM) that shader preparation emits (#770); the two selector translations of the command record's normalization, which sort a selector code into one of three groups (#779); four small queries of the swap chain's resource info (#784); and the block manager of the shader upload arena, which tiles its memory with range records kept in address order with a free list (#794). The fractal noise that the model wind samples for its gusts and its jittered direction (0x02a85e30) is replaced too, with results compared bit for bit (#792); the base noise under it stays original.

How the renderer learns what the game draws

Paleblood does not replay the finished GPU commands. Instead, the GPU library's replacements, with their packets unchanged, also tell Paleblood's renderer what they set, and the renderer draws that on your GPU (see Runtime: the renderer):

  • Observer calls in replacements #414: the blend, colour, depth, stencil, primitive-type, instance-count, viewport and draw replacements above each report the same value they write, with the place in the command buffer where they wrote it. Under the verification harness the calls do nothing. The depth and stencil clear values and DB_RENDER_CONTROL replacements report too #435.
  • Observed functions without replacements yet #416, #418, #435, #441: where a library function has no replacement, the runtime watches its arguments at its entry and lets the original run. These were setRenderTarget (0x014738b0) and the depth target (0x014739b0), now replaced (above), and still are the stencil references (0x01473190, 0x014731f0), the shaders' user-data writers (0x014761a0-0x014764a0), the indexed-draw setters and draw (0x01475270-0x01475320, 0x01474420) and two compute dispatch writers (0x01474c50, 0x0148a350).
  • The compute command buffer's user data #510: that buffer's six user-data writers (0x0148aad0-0x0148ada0) take no stage argument and were not observed, so a compute pass ran with whatever user data the record held from before; one colour lookup-table pass read another pass's table. They now report through the same observers as the stage writers.
  • Clinic loading #649, #654, #655, #652: the load into Iosefka's Clinic (12 November, local runs) reached five more library functions without replacements, now observed at their entry: the indirect-argument base (0x014742f0, which writes SET_BASE with base index 1), the indirect dispatch (0x01474de0, DISPATCH_INDIRECT with a data offset; the GPU reads the three workgroup counts at the base plus that offset) and the depth bounds setter (0x01473520), whose two bounds arrive as floats in xmm0 and xmm1 and are written as DB_DEPTH_BOUNDS_MIN and _MAX. The fourth is the shader-stage setter (0x01476030), which writes VGT_SHADER_STAGES_EN for five values only (0, 0x45, 0xad, 0xb0, 0x200) and nothing for any other: 0x45 turns on the local, hull and vertex stages of tessellation, 0xad adds a geometry shader, 0xb0 is export plus geometry. The engine's indirect draw caller (0x02569a4c) picks the local stage's user data exactly for 0x45 and 0xad. The fifth is the indirect draw (0x014744d0: command buffer, data offset, stage, and the SGPRs for the base vertex and start instance, each 0 for none), which writes DRAW_INDIRECT; the GPU reads the four arguments (vertices per instance, instances, start vertex, start instance) at the indirect base plus the offset. Its caller at 0x02569a89 passes no SGPRs. A related dispatch writer with a third argument (0x01474e80) is not observed yet.
  • Iosefka's Clinic #761, #802, #807: three more library functions are observed at their entry. The addressed indexed-draw writer (0x01474360: command buffer, count, index address) writes DRAW_INDEX_2; the YEBIS post-processing chain draws with it, so until it was observed nothing read the clinic's HDR scene target and the scene behind the HUD was flat grey. The clip-control setter (0x01476b30) writes PA_CL_CLIP_CNTL, which says among other things whether depth clipping is on. The viewport-scissor setter (0x014766d0: command buffer, viewport, left, top, right, bottom, and a seventh argument on the stack, the window-offset mode) writes PA_SC_VPORT_SCISSOR_n_TL and _BR. The game draws each deferred light as a full-screen quad once per 128x128 screen tile, with the tile as the viewport scissor (about 340 light draws a frame); without the scissor every tile's draw lit the whole screen, and the clinic was about eight times too bright. The PA_SC_MODE_CNTL_0 replacement now reports its value too, which turns the viewport scissor on (its packet is unchanged; recorded 98/98 and edge 15/15 again).

This needs the game library built from the decompilation (tools/boot.py --game-lib). In the maintainer's local runs it was enough to draw the studio logos and the title screen #441.

How the library functions were verified

Each replacement above was checked against the original instructions on constructed edge cases, which also caught deliberately broken variants; none was checked on recorded game frames. All are edge-verified. They are @evill33t's work, brought up to date with main and merged from the PRs named in brackets; #362 adds cases for the shader preparation's reset modes (from #350) and #352 derives the packet tests' addresses from the harness. The observer calls were added afterwards and leave the packets unchanged. The functions of 10 November (#482, #485-#487, #489) were checked the same way and are edge-verified; #489 lists each one's cases in its session report. The five context finishers of #557 pass 3, 6, 3, 34 and 3 cases; an independent re-review on the merged tree caught four of five planted mistakes, and the claim the fifth would have tested (the order of one scalar load) was taken out of its note.

Reference-counted objects: vtable slot 0 destroys, count at +0x8 (atomic). The engine shares this reference counting across systems since #185; the frame update was re-verified unchanged on all its recorded and edge cases.

Patch points

The frame-rate patches are described in Frame timing.

  • Uncap FPS++ makes the +0x70 child's step the flipper's measured frame time (+0x264) whatever the held flag says, through a small code cave inside the function, and drops the RendMan check. The 1/30 s it reads otherwise is the shared constant at 0x04d29170, which the 60, 90 and uncapped patches rewrite in the data segment.
  • Uncap FPS++ presents with flip mode 0 (no vblank sync) at the end of 0x025b2fb0.
  • Every frame-rate patch removes the first assertion of 0x00fbc3e0 (at least 3 base samples): at higher frame rates the blur gets fewer samples.
