AI

How enemies notice you and how their AI is run. The game steps a shared Havok AI world once a frame; each enemy's AI scripts call back into the game to read timers, numbers and stats; and the engine decides what each enemy sees and hears. This page covers the parts of that already rewritten as readable source.

At a glance

Scope
The per-frame AI world update and its debug drawing; the script bindings an enemy's AI scripts call; sight, hearing and the target list; the first pieces of the goal framework.
Verified
The frame update, the sight test, the perception update, the target list's main-target matching, most per-frame character queries and most timer, number and target-state bindings are checked against recordings from the game.
Edge-verified
Hearing (the ear's shape, the hearing test and the sound check), the goal registration options and the update-time scheduler, the stat bindings and several debug-draw helpers: checked from the code and constructed tests only.
Open
The AI world step itself (0x021cdad0), the target-list update that ages and promotes entries, how goals are run, and how any individual enemy decides what to do.

Summary

The game steps a shared Havok AI world through SprjHkAiManager (singleton 0x059401a0). Enemy behaviour itself is written in AI scripts that run on the game's script VM; each frame they call back into the executable through methods registered under the names the scripts use. Paleblood has replaced the engine side of several of those calls and the perception code they read from. None of this yet describes how a particular enemy or boss chooses its attacks.

What one frame does

Once a frame, ai_hk_frame_update_0222bc10 (0x0222bc10):

  1. Steps the Havok AI world with a fixed time step of 1/30 s.
  2. Checks its second flag. It is always set in the recordings. When it is set, the update:
    1. copies the frame object's matrices to the manager's view object;
    2. resets the render manager's debug state to its defaults and runs the AI debug display and drawing, made of the pieces below.
Piece What it does
Debug position the camera's position, or the player character's when the character manager exists
Group reset (0x02224090) one world area's debug step: its debug-menu entry cycles through added, shown, removed and hidden; with the step flag set, the area's blocks are stepped too
Debug display move (0x016334b0) moves the display to a position, staying put while its object stands on the same unflagged navigation point close to the reference
Debug flush (0x01633ac0) marks the objects of the entities the display's object links to
Debug end (0x0163bb50) draws the view's marks and the world's marks, then the subject's bounding box when asked (a box whose maximum is below its minimum in any lane is skipped)
Draw descriptor every AI object in the owner's groups, or the whole manager; its colour callback (0x02232a60) averages the palette colours of the layer bits both masks share
World draw (0x021d6ea0) sets four render-state settings, then draws every section of the AI world (nothing when the view has no debug renderer)
Axis frames (0x0135d810) ids looked up in the manager's id map, each drawn under the debug renderer's lock
Entity point (0x029ae440) the centre of one face of a nav-mesh instance, through its transform
Boxes the box mode at +0x2c68

The time step is a constant, not the measured frame time. Every frame moves the AI world on by 1/30 s however long the frame really took. That is why the frame-rate patches have to change it (see Patch points).

In the recordings from Iosefka's Clinic the update resets its three groups, copies the matrices and draws each AI object; the debug display, axis frames, boxes and the manager-wide draw stay off.

The frame update's helpers: PRs, contributors and evidence
  • @FFwLo replaced the debug-draw helpers: #815 (the axis frames and the layer colour callback), #885 (the world draw and the entity point) and #972 (the group reset and the debug display's move, flush and end).
  • The group reset, the entity point and the debug display move are now verified: checked against recordings from the game (the move's in #1079, with all of its paths covered by recordings and constructed cases together) and approved by an independent review.
  • The axis frames, colour callback, world draw, flush and end are edge-verified: from the code and constructed tests only. The clinic boots never call some of them, and others start with a short branch the recorder cannot yet hook.

What an enemy's scripts can ask

The engine side of the AI scripts is a set of small bindings that read or change a character's "think", the object that carries its AI state (#911):

  • Random draws. A float or an integer in a range, from a 20-bit fraction of the engine's random source.
  • Timers and numbers. Each think keeps 16 count-down timers and 64 free numbers, separately for the logic scripts and the goal scripts. The two sides check their indices differently (timers signed, numbers unsigned) and answer an out-of-range "is this timer finished?" differently; the replacements keep those quirks.
  • Target state. Four levels: normal, caution, find and battle, plus whether the state changed since the last think, and an optional forced state.
  • Stats. The SP, MP, HP and HP ratio of the character the script names, or 0 when there is none.

Alongside them run the per-frame questions a think asks about its own character (#920): its id, a negated column of its transform, a flag-module check, whether an effect on it carries one of three state bits, a ready check whose meaning is not yet known, link ids, and a pending AI event that is posted once the named character has it pending.

The random integer, the timer, number and target-state bindings and the character queries are verified from in-game recordings; the random float, the forced-state read, the stat bindings and the goal-side timers and numbers are edge-verified.

How an enemy sees you

Sight decides the "visible" flag the scripts read (#936, #958). In plain words:

  • Close by, at any angle. A character within the enemy's "nose" distance (plus both bodies' sizes) is noticed whichever way the enemy faces.
  • By eye. Further out, the target must be within an eye distance that depends on how dark it is where the target stands, scaled by how visible the target is and how sharp the enemy's sight is; measured from a point a little behind the enemy, and not closer than a starting distance. It must also be inside the enemy's width cone and height cone.
  • Line of sight. When the caller asks, a ray from the enemy's eyes to the target's must hit nothing in the physics world.
  • A target marked unseeable is never noticed, though the test still runs.

The sight test also places targets by direction ("is the target in front, behind, beside me?", 0x01693850), and a speed record keeps how fast the followed target is closing in over the last 30 frames.

The target list. What an enemy has noticed goes into a list of target entries. A noticed character refreshes its entry (marked visible this update) or gets a new one (0x016b2760). The entry with the highest priority is the main target, and every other entry for the same character, or for a place within half a metre of it, is marked as matching it (0x016b30a0, #920, #951, #961).

The perception update (0x016a85c0, #999) runs once per think. It counts down a perception timer, runs the target-list update (sight and hearing; still the original code), and then reads the target state off the list in a fixed order. The normal, caution, find and battle ladder lives in each target entry; this update only reports it, and the state it replaces becomes the previous state, so "the state changed" is true for exactly one think. It also answers whether the target faces the enemy and serves a one-shot "force battle" request.

Sight and perception: what is verified
  • Verified (checked against recordings from the game, each approved by an independent review): the sight test, the target-list refresh, the visible-flag lookup and the direction test (#997); the main-target matching (#951, whose recordings only held empty lists, so its matching logic rests on constructed cases, including the boundary case added in #961); the perception update and the current target's handle (#1079, from a capture boot of the clinic beast fight: 1493 of 1503 recordings pass, and 10 are set aside because the original itself leaves stack garbage in one byte or the recording is incomplete); the target speed record.
  • Edge-verified (from the code and constructed tests): the script-side visible-target and inside-target queries and the sight query's reset.

How an enemy hears you

Hearing is replaced in three steps, all edge-verified from the code and constructed tests (#1067, #1089, #1103). An enemy does not hear "noise" in general: each sound has a position, a range and a maker.

  1. The sound check (0x0169cef0) first decides whether this enemy may hear that maker at all, and how big the maker is. A character's sound is checked by team, using a table of which teams hear which (some sounds use the attack-hit team tables instead). An object's sound counts while the object still exists. Either way the sound then goes to the hearing test.
  2. The hearing test (0x0169d160) compares the sound's range, less the enemy's sound-cut distance, with the gap between them: the distance less both bodies' sizes. If the range covers the gap, the sound is heard.
  3. Otherwise the enemy's ear may still reach it: the ear reaches a little further, and its width and height angles decide. The ear's shape (0x0169da30) answers whether a sphere around the sound reaches the ear, within its height angle or along that angle's edge.

A heard sound is remembered: its position (unless the enemy already remembers a closer one) and, always, which sound it was.

Why hearing is not verified yet

Each function passes its constructed cases against the original (449, 561 and 1642), and the deliberately wrong versions fail, except ones shown to be equivalent. The ear's shape cannot be recorded yet: one of its arguments arrives in a vector register the recorder does not capture. No recording from the game covers any of the three.

Goals: the first pieces

An enemy's AI plans with goals: its scripts add goals by id, each goal id having a definition registered when the scripts load. The first part of that framework is replaced and edge-verified (#1109):

  • Registration options. Four script functions the AI scripts call at load for a goal id. Each finds the id's definition and sets one option: the goal has no update, the update-time range it is updated in, the goal cannot be interrupted, or combo attacks may be cancelled.
  • The update-time scheduler's reserve (0x016a3be0). It spreads AI updates over frames: a ring of 100 one-frame slots, at 30 frames a second, each counting the updates booked in it. A booking goes into the slot its delay names, or, when that slot is full, into the next slot with room, and the delay comes back moved to match. Nothing in the executable calls it directly.

How goals are run, interrupted and ended is not replaced yet.

What this page does not tell us

The replaced code establishes how the AI world is stepped, what the scripts can read, and how sight, hearing and the target state are computed. It does not reveal any individual enemy's decisions, attack timing or boss phases: those live in the AI scripts and the goal code that is not replaced yet. Gameplay observations alone will be labelled as observations until their implementation is traced.

Structs and globals

Owner of the update. The AI objects sit two levels down: the owner holds groups, each group holds elements, and each element holds a list of objects.

Offset Field
+0x2bc8 group count
+0x2bd0 groups, 0x20 bytes each: element count +0x8, elements +0x10
(element) 0xb0 bytes each: object count +0x58, object list +0x60
+0x2c18, +0x2c20 debug display
+0x2c68 box mode
+0x2c90..+0x2c98 flags
+0x2cb8 axis-frame pairs (id, index), +0x2ec0 of them

SprjHkAiManager. AI world +0x10 (its id map at +0x10), view object +0x20.

The think's perception record sits at think +0x560; the script bindings read the current and previous target state from it, and a forced state at think +0x9a8 (-1 when none).
