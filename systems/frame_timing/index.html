Frame timing

How the game paces its frames: a frame step that runs once a frame, a frame limiter that waits out each frame's budget, and a task manager that runs the frame's work.

At a glance

Scope
Frame pacing, delta time, vsync and the main loop's time step.
Verified
The frame step, the frame limiter, the flipper constructor and the task manager's frame path are replaced and verified.
Our option
BB_TARGET_FPS does in code what the community frame-rate patches do in these functions.
Open
A few limiter fields, the owner of the 0x0111a... clock layer, and most functions the 60 FPS patches edit.

Summary

The frame step

frame_timing_frame_step (0x02418d20) runs once per frame. In order, it:

  1. checks that the SprjWindow is running;
  2. creates the SprjFlipper singleton on first use (frame_timing_flipper_init, 0x02434520);
  3. runs the frame limiter, frame_timing_pace_frame (0x02434770), a method of that flipper;
  4. runs the task update with a small 1/30 s descriptor;
  5. asks a quit gate and a quit query, and returns whether the game keeps running.

Both the limiter and the frame step are replaced and verified.

The frame limiter

Each frame the limiter does four things.

It applies the flip mode. The constructor reads the mode from the config value Game.FlipMode. A pending mode at +0xc replaces the current one at +0x8 when +0x276 is set. The mode chooses the sync interval (stored at +0x10) and the frame interval (a float at +0x18):

Flip mode Sync interval Frame interval
0 and 1 2 1/30 s
2 1 1/60 s
3 and 4 1 1/30 s

It reads the time with gettimeofday, in microseconds.

It waits out the frame's budget, shortened when recent frames ran late. A switch in the build (0x013e3980, always 1) selects the spinning wait, which polls the clock without sleeping (hundreds of thousands of reads in a long frame). A sleeping wait is compiled in but unused.

It keeps the last 32 frame times in a ring (index at +0x260) and derives a frame rate from their average (+0x2b8).

Which clock the game reads

gettimeofday supplies wall time, so it is not guaranteed to be monotonic. The frame limiter's confirmed call passes a null timezone pointer. The game's separate verified clock helper invokes sceKernelClockGettime with ID 4, identified as CLOCK_MONOTONIC; that does not establish the IDs accepted by the imported libc clock_gettime wrapper. See the runtime system-call notes.

Two other clock functions are easy to mistake for part of the limiter:

  • 0x004632d0 is a small gettimeofday helper in microseconds that the stock game never calls: nothing calls it directly, and no relocated pointer (vtable or table slot) points at it. The frame-rate patches overwrite it and its neighbours with their own code (a code cave), so it is not replaced.
  • The millisecond clock frame_timing_get_monotonic_ms (0x0111a7f0), its microsecond twin 0x0111a760 (replaced too, edge-verified, by @evill33t in #103) and the sleep wrapper 0x0111a880 (now replaced, see below) are not on the limiter's path. They look like the timing layer of a separate subsystem.
Correction (2026-10-06): the 0x0111a... clocks are a separate layer

The millisecond clock frame_timing_get_monotonic_ms (0x0111a7f0), its microsecond twin 0x0111a760 and the sleep wrapper 0x0111a880 are not on the limiter's path. All 52 of their callers sit in one region (0x0110e...-0x0121b...) that shares its own helpers, and no frame-rate patch touches any of them: they look like the timing layer of a separate subsystem (unidentified; possibly middleware). Their system label may move once that subsystem is known.

The fixed-step state methods

Many small objects in the game advance in fixed steps of 1/30 s, whatever the real frame time is. The community "60 FPS++" patch changes those steps to 1/60 s, so knowing exactly which functions it edits, and what each belongs to, is part of running the game faster than 30 FPS. Paleblood has replaced a growing set of them in game/frame_timing/fixed_step_states.cpp.

The latest belong to the Chalice Dungeon gate, the object behind the ritual altar:

  • Its steps have names. The gate (SprjDungeonGateIns) keeps a table of 24 steps whose names are in the executable. They give its states their meaning: loading a channel, no chalice, a local or online ritual, a local or online dungeon, and an error display.
  • Finding the gate. The game finds the current gate through SprjHolygrail. The highest of seven event flags, 9020 to 9026, picks one of eight gate slots; with none set, it uses the last slot.
  • Waiting for it. Two methods advance the gate while it is busy and are done once it is idle. Two more wait until it is idle in a dungeon mode, or in a ritual mode.
  • Leaving a mode. One method, held by an object that points to the gate, takes the gate out of a ritual or dungeon mode (request 7) and out of the error mode (request 10), around a check on the gate that reads the online manager, and reports when the check passes in the online dungeon mode. What its caller does with that answer is not known: the caller ignores it.
  • The check itself. It passes only when the gate is idle in mode 1 (no Holy Chalice), four bytes of the online manager (FrpgNetMan) allow it (one set, three clear; what they mean is not known), and the id it is given is set. It then looks up an object for that id and keeps it as the gate's handle, a reference-counted pointer: the engine counts how many holders an object has and destroys it when the last one lets go, so swapping the handle drops the old object's count and takes one on the new. Finally, if the gate is still idle, it gives the gate request 6 and reports success. That the id names an online session is a guess.
  • Its sibling, the entry check. It opens with the same gates, then searches a list for the first entry with a given key that holds an object, and keeps that object as the gate's handle in the same way, with request 4 instead of 6. When the gate becomes busy while the old handle is let go, it stops and reports failure rather than trying the next entry.
  • Letting the handle go again. In a ritual mode a third method resets the handle. In the local ritual mode it always may; in the server ritual mode only when the online manager's bytes allow it and a flag bit in the handled object is clear. It clears one word of that object, hands the handle to a routine not yet analyzed (0x01e9cb80), and gives the gate request 8. A fourth method does the same under the same rules but first gathers the gate's sixteen slots: each active one goes into a short list (its key, its number, and a value the caller supplies for it), built on one of the engine's memory heaps. With no active slot it does nothing; otherwise it hands the handle and the list on (0x01e9cd20, not yet analyzed), gives request 8, and then frees the list's memory.
  • Passing the handle on. A readiness check lets the gate go on when it is idle in a ritual or dungeon mode and the online manager allows it; in the server modes the handled object must also have one word at zero. Two methods that differ only in a "kind" number (1 or 2) run that check, clear two words of the handled object, hand the handle on with the kind (to one routine in the local modes, another in the server modes, neither analyzed yet), and give request 9.
  • Creating the handle. Two methods make the handle in the first place, both only while the gate is idle in mode 1. One drops the old handle, builds a new handled object from two blocks of data, a block of the online manager and a name (the current name entry's, or a default), and gives request 3. The other reads four "levels" from event flags: for each of four base flags, the highest level from 9 down to 1 whose flag is set (flag numbers 6228 to 6287, every seventh one belonging to the same column). It builds the handled object from those four levels and gives request 5. What the levels and the flags stand for in the game is not known yet.

The millisecond sleep wrapper (0x0111a880), which is not on the limiter's path, is replaced too. It converts the engine's millisecond delay to the kernel's microseconds. It multiplies in 32 bits, as the original does, so very large delays wrap, and it always reports success.

Small clocks, waits and stopwatches

Nine small helpers that read the time or sleep are replaced and edge-verified (Paleblood #514). None of them is on the limiter's path:

  • Time of day. frame_timing_time_of_day_us (0x02e61140) gives the time of day in microseconds; frame_timing_time_of_day_ticks (0x01088550) divides it by an owner's own tick length; frame_timing_time_seed_words (0x02e61280) returns four seed words, the time itself and the time plus a counter that steps by two on every call, so two calls in the same microsecond still differ.
  • Random state. frame_timing_thread_random (0x02c6d580) returns the calling thread's random number state (a thread-local variable), seeding it the first time from the low 32 bits of the time in microseconds. About sixty callers fetch it.
  • Stopwatch. frame_timing_stopwatch_start (0x01448580) stores the seconds since the game started, only when the stopwatch reads exactly zero; frame_timing_stopwatch_stop (0x01448620) adds the time since that start to two running totals. The task frame brackets work with them.
  • Waiting for a job. frame_timing_job_wait (0x024bdd40) polls a background job's state until it is finished, sleeping 1 ms between polls; frame_timing_job_take_result (0x024bd150) takes a job's result, polling, waiting or taking at once depending on its mode, and counts one more holder of the result under a lock all jobs share.
  • Sleep. frame_timing_posix_sleep_ms (0x00466810) sleeps through the POSIX usleep and always reports success.

The community Performance Patch turns the stopwatch into a no-op and shortens the job waits' poll to 0.1 ms. Those byte edits do nothing while these functions are replaced, and there is no option for them yet.

How these were verified

Each function's edge cases pass against the original (10 to 55 cases each), deliberately wrong versions fail, and an independent review approved all nine. They are edge-verified: none has been recorded in a game run.

Frame time in game logic

The frame step also passes time into character updates. One verified update accumulates a per-frame points value using that time and retains fractional progress between frames. Its evidence and unresolved stat identity are documented in Stats & Progression.

The task manager's frame

Each frame, the frame step hands the frame's work to FD4::FD4TaskManager (singleton 0x058b2e30). The path is a good example of how an engine brackets its work so that nothing runs twice or half-finished:

  1. 0x024512a0 fetches the task manager and runs every task group (0x01388c60, mask -1).
  2. 0x01388c70 refuses to start while a frame is already running (a busy flag at +0x38). It flushes the task queue that collected work since the last frame (0x0143e490: lock, run each queued object, destroy and free it, empty the list, unlock), steps the worker threads' queues (0x014400a0), and publishes the frame's value (0x0143f9f0 copies a float from the frame's information to a global).
  3. With the busy flag set, it calls the dispatcher (+0x40, virtual +0x30), which runs the frame's tasks; then it clears the flag, flushes the second queue and steps the workers again.

The dispatcher (0x0138a370) is the last link: when its group record asks for it, it wakes every registered task (76 in Iosefka's Clinic), then fills a job with the record, the task table and the group mask and runs it through the same five steps as the workers. Each of those tasks is a piece of the game's own per-frame work, the next layer to map.

On 13 November contributor @FFwLo replaced the parts this path still called as originals, all edge-verified (#814). A worker holds a list of 16-byte slots, each a lane and the batch given to it, and a busy byte: 0x0143e030 puts a batch in a slot (refused while the worker is busy, for a null batch or an index past the slot count); 0x0143de20 marks the worker busy and starts every slot that holds a batch, a lane in mode 0 running on the calling thread and any other lane on its own thread; 0x0143deb0 runs the mode-0 lanes; 0x0143df10 waits until no lane is running, spinning on lanes that belong to other threads as the original does; and 0x0143ec40 frees a task's pending items under the task's lock. The per-frame task's own helpers followed (#793): two profiling stopwatch brackets and the end-of-frame tick of ten profiling stopwatches, which do nothing unless the profiling switch byte is set, and the item list and listener list updates that pass the frame-time descriptor on. The seeding of a thread's random generator (0x024f8110) fills four 32-bit words from a 32-bit seed with a 64-bit linear congruential step (#790); it uses the seed it is given and reads no entropy of its own.

Patch points

The community frame-rate patches (Kyo; Lance McDonald and Kyo for Uncap FPS++) edit three of our functions; disassembling the limiter with and without each patch shows exactly what they do:

  • Limiter (0x02434770): the flip-mode switch always takes one entry (mode 2 for 30 and 60, mode 0 for uncapped) with patched values: interval 1/30 s (30), 1/60 s (60) or 1/240 s (uncapped), and a zero vblank word (+0x268). Every override is skipped: the reset flag (+0x2c4), the two override counters (+0x2bc, +0x2c0) and the two clear flags (+0x271, +0x272). At the end the sync interval (+0x10) is kept on late frames instead of zeroed.
  • Frame step (0x02418d20): the frame time passed to the task update starts at 1/60 s (30: 1/30 s), and when the flipper's interval is not 1/30 s it becomes the measured frame time (+0x264) clamped to [interval, 1/30 s]. This is the patches' delta time: the game logic advances by how long the frame really took. The patch drops the SprjTask check to make room.
  • Flipper constructor (0x02434520): the first interval is 1/60 s (60 and 90).
  • They also edit 59 other functions; 12 of them are dead code in the stock game (no caller, no relocated pointer). Many of the rest pass the same 1/30 s frame-time descriptor to an owner object, which the 60 FPS patches change to 1/60 s.

The patches also rewrite dozens of shared constants in the data segment (the 1/30 s step at 0x04d29170 becomes 1/60 s, 1/90 s or, uncapped, 1/60 s), which code we have not replaced reads too. BB_TARGET_FPS covers only the replaced functions, so it is meant to run together with the patch; option checks run both sides on the patched image for that reason.

How the patch edits were mapped

tools/patch_overlap.py maps every patch line to the function it falls in, and lists the patches that do nothing while our hooks are installed.

Our option: BB_TARGET_FPS

BB_TARGET_FPS=30, 60 or uncapped does in code what 30 FPS++, 60 FPS++ and Uncap FPS++ do in the three functions above. Unset keeps the original behaviour exactly.

The option has to cover the frame step as well as the limiter. A faster limiter alone would still tell the game logic that every frame lasts 1/30 s; the delta time comes from the frame step (see the patch points above).

The other functions the patches edit are not replaced yet, so a 60 FPS game would still need the community patch for them; its edits inside our three functions do not run, and our option does their part.

A second option, BB_LIMITER_WAIT=sleep, makes the limiter use the sleeping wait the game carries but never selects: it sleeps until about 5 ms before the frame's end and spins the rest, so a fast machine does not keep a core busy waiting.

How the option is checked against the patches

Each part is checked against the patch itself: tools/verify.py run --patch FILE:NAME --env BB_TARGET_FPS=... runs the original with the patch's bytes applied against our replacement with the option, on the edge cases and on frames recorded in the game at 60 FPS.

Recorded frame times at 60 FPS (October 7)

A saved October 7 measurement with the external host scaffold, all replacements hooked, and BB_TARGET_FPS=60 reports a median frame time of 16.67 ms and p99 of 16.69 ms. That historical result is recorded in Paleblood's status evidence; it is not a real-display result from Paleblood's project-owned boot path.

History: the first version changed only the limiter

An earlier version only changed the limiter. Because the hooked frame step no longer ran the patches' delta-time code, at 60 FPS the game logic would still have been told every frame lasts 1/30 s; checking against the patches found that, and that the limiter's own settings differed.
