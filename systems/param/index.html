Parameters

Most of Bloodborne's numbers are not in its code. Weapon damage and scaling, armor, items, the effects of consumables and blood gems, enemy stats and AI tuning, item drops, shop stock, the lamps you warp between, and the colors and layout of menus all live in parameter tables: PARAM files the game loads. The code asks a table for a row by its id and reads fields from that row. This page covers the part of the game that holds those tables and answers those questions. It does not describe what the tables contain, which is game data.

At a glance

Scope
Paleblood's game/param/: the solo parameter repository, the per-table row lookups, the equipment, menu, map and return-point lookups, row names and rows by position, table walks, the attack and behavior pairs, gem searches and character creation's face tables.
Verified
Every replaced lookup is edge-verified against the original on invented tables. None is verified yet: none has been checked on frames recorded from a real game run.
Open
The loader that reads the files and builds their search index; most header words; why the row-name lookups exist in the retail build.

Summary

The solo parameter repository

All the tables a single-player game needs are kept in one object, the SoloParamRepository, a singleton (0x05940340). It has one slot per table type, 62 types in all. A slot records whether its table is loaded, and points through a resource holder to the loaded file.

Every lookup first asks the repository for its table. A missing repository is reported with the engine's singleton check (see Engine) and then read anyway, as the original does. A slot that is not loaded gives "no row".

Inside a PARAM file

A PARAM file is a header, a list of row descriptors, and then the rows' data and names. Bloodborne's files follow the layout the modding community documents for FromSoftware's games:

  • The header holds the row count (16 bits), a data version (16 bits), and a format byte with a flags byte after it.
  • Format 2 files have a 48-byte header followed by 12-byte descriptors (row id, data offset, name offset). Later formats have a 64-byte header, and from format 4 on a flag switches to 24-byte descriptors with 64-bit offsets.
  • Offsets count from the start of the header. A name offset of 0 means the row has no name.

The search index

The game does not search the descriptors directly. Each loaded file is followed by a search index: (row id, row number) pairs sorted by id, placed at the file's size rounded up to a multiple of 16. The size is the word at -0x10 from the header. Every lookup by id is a binary search of this index, with ids compared as unsigned numbers. The code that loads the files and builds the index is not replaced yet.

How the game asks for rows

The game has a separate compiled copy of each lookup for each table type that needs it. They are all built from a few templates, and Paleblood's replacements share one implementation of each.

  • Row by id. It returns the id asked for and the row, or no row. A negative id returns at once, without touching the repository. Most types use this plain form (#687); GemGenParam has two identical copies. A few copies add something:
    • SpEffectParam and TalkParam also return the table's data version.
    • NpcThinkParam stores two extra words beside the result, unread.
    • ActionButtonParam and ReturnPointParam fill a result that starts +0x8 into the object they are given (#697).
    • ItemLotParam gives no row unless the table's data version is 2 or later (#697).
    • DungeonFeatureParam copies a header word (+0x06, meaning unknown) to a global on every search, found or not (#697).
    • NpcParam also returns that header word and the data version, and reports a table of version 2 or older through the engine's error report, then searches it anyway (#714).
  • Equipment (#697). The last two decimal digits of a weapon or armor id are its reinforcement level. The lookup finds the base item's row (the id rounded down to a multiple of 100), then the ReinforceParam row for the item's reinforcement type plus the level. Without a base row it still asks the reinforcement table, for id -1.
  • Runs of rows (#697). Character creation's list items and some menu tables are read as consecutive ids: the lookup returns the first row and how many rows follow it without a gap. The NewMenuColorTableParam run falls back to 16 rows built into the executable when the table has none.
  • A built-in fallback (#697). The menu property lookup uses the table's row when there is one, otherwise the built-in row with that id, otherwise the first of 13 rows compiled into the executable.
  • Row names (#714). A row can carry a name (an editor's label, kept as text after the rows). Ten table types have a lookup that returns it, or nothing; GemGenParam again has two copies. Unlike the data lookups, this one checks the index's row number against the row count.
  • Row by position (#714). CharaInitParam, EquipParamGoods, Magic and MenuColorTableParam can be read in file order: row n with its id, or id -1 when the table is shorter.
  • Maps and lamps (#714).
    • GameMapParam, a map's lighting set-up, is found by the map's number. A map named mAA_BB_CC_DD is row AABBCCDD, and maps without their own row use row 0.
    • ReturnPointParam lists the return points: the lamps players warp between and revive at. It is searched row by row, in file order: the warp-menu slot of a lamp, the lamp in a warp-menu slot, or every lamp with a warp-menu slot in one map area and block.
  • Walking a table (#730). The equipment and item tables (weapons, attire, badges, items) have a row count, the id after or before a given id (rows are sorted by id, so this steps through the table; a negative id starts at the first or last row) and a list of every row id. The badge list leaves out rows with a negative value in one field, whose meaning is unknown.
  • Filtered walks (#823). The attire table can be stepped through among rows with a given byte at +0xd2 only, and the weapon and attire "version" lists add, after each row's id, one id per upgrade level the row lists. Weapons can also be stepped through until one with a given property bit, and three set checks (goods, attire, weapons) build a small cache of set numbers on their first call.
  • Pairs of tables (#733). The attack lookup picks AtkParam_Npc or AtkParam_Pc, and the behavior lookup BehaviorParam or BehaviorParam_PC, by a 0/1 argument.
  • Searches by content (#733). The gem effect for a group at a level (the highest rank up to the level among rows whose level range holds it), GemGenParam row numbers by id range, and GemCategoryParam rows by one of two fields. After loading, the chalice weapon and attire generation tables are fixed up in place: an entry index above 63 is marked as none.
  • Special cases (#823). GameAreaParam ids 2900100 to 2900799 all read row 2900100. ItemLotParam_Lvdep picks, in an id's group of 100, the last consecutive row within the group's first id plus a level. The lock-on camera's largest distance (LockCamParam +0x10) falls back to row 0, then to a value the camera object keeps.
  • Character creation's face (#724). The FaceGenParam row the creation screen builds (50 geometry and 50 texture sliders, eight parts each with a colour, decal placement) and the FaceParam presets (body proportions, age, gender, caricature, asymmetry) are edited in place by setters. The originals never handle a missing row (they search forever or write through a null row); the replacements stop by name there.
How the lookups were verified

Each replacement is readable C++ in game/param/ and passes verify.py against the original on invented tables built by the fixtures beside it (synthetic cases, never game files). They are recorded as edge-verified in #687, #697, #714, #724, #730, #733 and #823. None has been checked on frames recorded from a real game run, so none is verified. The row-name lookups did not run in the coverage boots #714 describes.

Structs and globals

SoloParamRepository (0x05940340): the table slots start at +0x70, one per type.

Offset Field of a slot
+0x0 loaded flag (zero until the table is loaded)
+0x8 resource holder; its file is at holder +0x70, and the table header at file +0x70

PARAM header (only the fields the lookups read)

Offset Field
+0x06 header word, meaning unknown (NpcParam and DungeonFeatureParam pass it on)
+0x08 data version
+0x0a row count
+0x2d format
+0x2e format flags (0x2: 64-bit offsets, from format 4 on)

A lookup's result: the id at +0x0, the row at +0x8; the four bytes between are left as they were.

Globals: the built-in menu property rows (0x05528730), the built-in NewMenuColorTableParam rows (0x055286e0), and where the DungeonFeatureParam lookup copies its header word (0x05992cb0).
