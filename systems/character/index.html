Character

Every character instance in the game is updated once a frame. This page covers one of those updates (throw events, the regeneration of a points stat, and the hand-off of frame time to the character's modules), the module updates it leads to, and the handles that name the items a character holds.

At a glance

Scope
character_frame_update_01cbdb20, one of the per-frame updates of a character instance; the throw event and four module updates beneath it; the item handles of the game's item manager.
Verified
character_frame_update_01cbdb20 (the throw event, the points regeneration with its fractional carry, and the frame-time hand-off) and the five item handle functions. The throw event, the module updates and the item manager's free are edge-verified.
Open
Whether the points stat is stamina, whether the update belongs only to the player, what the five refilled counters are, and the rest of the instance layout.

Summary

Character instances (ChrIns in FromSoftware's engine) are updated once a frame through virtual calls on each instance. character_frame_update_01cbdb20 (0x01cbdb20) is one of these updates.

What the update does

  1. Fires a pending throw animation event (W_ThrowAtk or W_ThrowDef) and clears the request.
  2. Regenerates a points stat that floors at -50 and caps at a maximum (see below). It reads like stamina.
  3. Hands the frame time to the character's modules, copies a few parameters, and builds (then drops) a wide string of the character's name with the thread's allocator. Nothing reads the string; it looks like the remains of debug code. In the recordings from Iosefka's Clinic the name string is never built.

How the points stat regenerates

The regeneration rate is a product of four terms:

Text Only
rate = parameter byte × 0.01 × per-character multiplier × virtual factor

The multiplier lives at +0x16c on the instance, and the last rate is kept at +0x39c. Each frame the update:

  1. multiplies the rate by the frame time (read from +0xe0);
  2. adds the whole part of the result to the points (data module +0x134), capped at the maximum (+0x138);
  3. keeps the fraction at +0x168 and adds it in on the next frame.

Carrying the fraction means a rate too small to add a whole point in one frame still adds up over several frames instead of being rounded away.

Two switches stop the stat from dropping: bit 7 of the data module's +0x200, and the debug flag 0x0593e88a next to the WorldChrManDbg singleton.

Points, stamina and the player

The source calls this value points. Its relationship to stamina, and whether this update belongs only to the player, are not established. The current evidence-backed account is in Stats & Progression.

The throw event and the module updates

The calls the frame update makes are being replaced one by one, by contributor @FFwLo. All five below are edge-verified: their constructed cases pass against the original and deliberately wrong versions fail, but none has recorded cases from a game run yet (the first boot tried for them stopped at the title screen, before any character is updated).

  • The throw event (0x01e19e20, #965) looks the event's name up in the behavior manager's table and, for a known name, appends the event to the character's behavior graph, growing its event ring (doubling, or to 8 when empty) when full. Nothing happens until the behavior manager is ready. A quirk is kept: the original never fills four bytes of the event it builds, so they come from whatever was on the stack, and the replacement passes the same bytes on.
  • Four module updates (#884):
    • an event request update (0x01e59250) fires a pending numbered animation event by name, unless a gate flag, a module flag or an active throw suppresses it, then clears the number;
    • a counters refill (0x01e5c440) adds to five counters a per-second rate times the frame time, carrying the fraction to the next frame like the points stat, flooring at 0 and capping at each counter's maximum. What the five counters are is not established;
    • a state flags update (0x01e4a490) decides whether the character is shown, from its flags, its animation state, its parameters and the draw target, and folds that into two sticky bytes; it also counts frames and sets a link flag;
    • an AI display update (0x01cd92b0) hands the character's two positions to the AI debug display and points its markers at them, when its readiness check passes.

Item handles

The game's items (SprjGaitem) are named by handles into the item manager's table of 0x1000 slots. How characters use these items is not mapped yet. A handle names a slot when its managed bit is set and its index is valid, and the slot is live while it holds that same handle; each slot counts its references. Five small functions copy, release, move and resolve these handles, and the last release frees the item (#967). All five pass cases recorded in the game and were approved by an independent review, so they are verified (#1001). Quirks kept: the copy, release and move do not check the index against the table, a missing manager is reported and the handle then treated as unmanaged, and a failed state check during resolve is reported and the handle resolved anyway.

The free itself (0x01e86e60, #1078) is edge-verified. It does check the index. It destroys the slot's item and returns its memory to the heap that owns it, gives the slot the next generation of its handle (so old handles to it stop matching) with no references, and puts the index on a ring of freed indices. It has no recordings yet.

Scope still to map: the character instance layout, the modules (+0x3b0), the parameters, the other per-frame updates.

Patch points

The frame-rate patches (see Frame timing) replace the frame time read from +0xe0 with a constant:

Patch Frame time used
30 FPS++ 1/27 s
60 FPS++ 1/54 s
60FPS (no deltatime) 1/50 s
90 FPS++ 1/80 s
Uncap FPS++ the real frame time

BB_TARGET_FPS does the same for 30 and 60. A fixed time slightly longer than one frame (1/27 instead of 1/30) speeds regeneration up a little; why the patch authors chose it is an open question.

Open questions

  • Is the points stat stamina? A floor below zero would fit a stat that can be overspent.
  • Why the patches choose 1/27 and 1/54 rather than 1/30 and 1/60.
