Runtime system-call notes

What each runtime system call is for, what it must do, what the game was seen to do with it, and how Paleblood's runtime answers.

Two rules the runtime follows

Most calls below share the same shape, so it helps to know it first.

  • Stopping by name. When the PS4's answer to a call is not established, the runtime does not guess. It stops the process (a "fail-loud diagnostic") and names the call the guest made. A registry entry that stops like this is not an implementation.
  • Two error conventions. Many calls exist under an SCE name (scePthread…) and a POSIX name (pthread_…). As with the mutex functions (runtime/syslib/kernel_mutex.c), the SCE name returns 0x80020000 plus the error number, and the POSIX name returns the number itself.

What the calls are for

getpagesize
Takes no arguments and returns the system's memory page size in bytes. The number is platform-specific. It is not in current POSIX; portable code uses sysconf(_SC_PAGESIZE).
getpid
Takes no arguments and returns a pid_t for the calling process. POSIX defines no error return. What a process ID means, and how long it lives, is platform-specific.
clock_gettime
Reads the clock chosen by clock_id into a struct timespec: seconds (tv_sec) and nanoseconds (tv_nsec, from 0 through 999,999,999). POSIX returns 0 on success, and -1 with errno on failure; an unsupported clock ID is EINVAL.
gettimeofday
Reads wall time into a struct timeval: seconds since the Epoch and microseconds (tv_usec from 0 through 999,999). Wall time can jump, so it is not a monotonic clock for measuring elapsed time. POSIX.1-2024 removed the interface.

What the game does with them

The executable imports getpagesize and gettimeofday from libScePosix. The game's bundled libc.elf imports clock_gettime, getpagesize, getpid, and gettimeofday from libkernel. These imports tell us which names are needed, not every argument or how the PS4 behaves.

  • The frame limiter reads the time with gettimeofday and passes null for the timezone argument.
  • A separate verified game helper calls sceKernelClockGettime with clock ID 4, identified as CLOCK_MONOTONIC.
  • The bundled C library's time() calls clock_gettime with clock ID 13 and keeps only the seconds. That is FreeBSD's CLOCK_SECOND, whose answer is the wall clock in whole seconds.

Clock ID numbers are implementation-defined. The PS4's kernel descends from FreeBSD, and both observed IDs fit FreeBSD's numbering, so the runtime answers FreeBSD's realtime (0), monotonic (4) and second (13) clocks from your computer's clocks (#164, #165). Any other ID stops by name, or answers EINVAL under the SCE name.

Working out the page size

The page size is a good example of how far file evidence goes, and where it stops. getpagesize is the only page-size query the game has: nothing imports sysconf.

  1. Observed in the game files. Every loadable segment of the eight images is aligned to 0x4000, and each segment's file offset and address differ by exactly 0x4000. Three call sites use the result the same way: they accept it only if it is a power of two and cache it next to three fixed sizes (0x10000, 0x40000, 0x200000). Nothing else reads that cached value, and nothing compares it with a constant.
  2. Inferred, with its assumptions. If the PS4 loader follows the usual ELF rules for these segments, the page size cannot be larger than 0x4000; any power of two that divides 0x4000 would fit. Narrowing that to 4 KiB, 8 KiB or 16 KiB also assumes a page is at least 4 KiB, which is our assumption, not an observation. The game's own check accepts every power of two, so it does not pick one either.
  3. Unknown. The actual value. Stock FreeBSD on AMD64 uses 4096, but that describes the PS4 kernel's ancestor, not the console.

For a month both getpagesize entries stopped by name. On 10 November the maintainer ruled on it (#528): the runtime answers 16 KiB. No console measurement exists, but every public PS4 runtime and port answers that value, and it is the largest the files allow, the alignment every segment already has. It is a ruling, not a measurement, and the page says so. Paleblood's loader does not depend on the page size either way: it copies each segment to its exact address.

Threads and yielding

Call Status What the runtime does
scePthreadEqual implemented Compares guest thread handles; zero means different.
sched_yield implemented Yields the host thread and returns zero.
scePthreadYield implemented Yields the host thread and returns zero (#308).
pthread_self implemented Answers what scePthreadSelf answers.
scePthreadKeyCreate, scePthreadKeyDelete, scePthreadGetspecific, scePthreadSetspecific implemented Per-thread values, following FreeBSD libthr's thr_spec.c. At thread exit each destructor runs, for up to four rounds; past the POSIX minimums (128 keys, 4 rounds) it stops by name (#298, by @EzequielRindello).

A guest thread runs on a host thread. A thread handle is an opaque pointer to the runtime's object for that thread, so these calls work by comparing or returning those pointers.

  • scePthreadEqual asks whether two handles name the same thread. The runtime compares the opaque object pointers used as guest thread handles: zero means different, nonzero means equal. The exact nonzero value the PS4 returns, and its behavior for a null handle, are not established.
  • sched_yield lets other threads run. The runtime yields the calling host thread and returns zero, following the POSIX/FreeBSD contract. A host failure stops by name. The unit test checks the result; it cannot prove that the host scheduler ran another thread.
  • On macOS the registry is gathered the same way, from a section of the Mach-O binary instead of the ELF one (#216); Linux is unchanged.
  • Darwin (macOS) versions by @evill33t, each tested on their own Macs, with Linux unchanged: timed locks and condition waits on native try-locks and relative waits that recheck the original deadline (#576), direct memory backed on Darwin (#580), and guest worker threads with their thread-local storage on x86-64 (#583). The game does not run on macOS yet.
  • scePthreadYield does the same (#308). Its PS4 signature is not published (FreeBSD's analogue returns nothing, Linux's returns an int), but answering zero is right either way: a caller of a function that returns nothing never reads the result, and zero is the int version's success. Every one of the game's 26 direct calls ignores the result.
  • pthread_self (libScePosix) returns the calling thread's own handle. It answers exactly what scePthreadSelf answers. With no guest thread registered on the host thread, it stops by the name the guest used. POSIX defines no error return.

These are runtime services, not new decompiled game functions. The boots recorded on merged main since then pass through them.

Thread attributes

Call Status What the runtime does
scePthreadAttrSetdetachstate, pthread_attr_setdetachstate implemented Records the state; bad values give EINVAL.
Default detach state (fresh or copied attribute) unresolved Thread creation stops by name instead of assuming joinable.
pthread_attr_init, pthread_attr_destroy implemented Allocate and free attributes under the POSIX names.

A thread attribute is a small object a program fills in before creating a thread: it describes how the new thread should start. The game creates and frees these objects, and sets one field of them, the detach state.

Creating and freeing attributes

eboot imports pthread_attr_init and pthread_attr_destroy from libScePosix, next to the SCE names the runtime already had.

  • Init allocates the attribute and stores it in the variable; ENOMEM when it cannot (POSIX; FreeBSD libthr's _pthread_attr_init).
  • Destroy frees it and empties the variable; EINVAL for a missing or empty variable (libthr's _pthread_attr_destroy).
  • A missing variable passed to init is undefined in POSIX and unchecked in libthr. The runtime answers EINVAL under both names, as the SCE name already did and as the mutex attribute calls do. No PS4 source or call site says otherwise.

An attribute made under one name can be freed under the other.

Setting the detach state

eboot and libSceFios2.elf import scePthreadAttrSetdetachstate from libkernel, and eboot imports pthread_attr_setdetachstate from libScePosix (symbols/imports.csv).

  • What the call does. A thread created with the attribute starts detached for PTHREAD_CREATE_DETACHED (nobody waits for it to finish) and joinable for PTHREAD_CREATE_JOINABLE (another thread can join it). This is POSIX pthread_attr_setdetachstate.
  • Invalid detach state. POSIX and FreeBSD's pthread_attr(3) both make any other value EINVAL.
  • Invalid attribute variable. POSIX leaves a null or uninitialised attribute undefined and only recommends EINVAL, and the FreeBSD manual lists no error for it. The behaviour comes from FreeBSD libthr's _pthread_attr_setdetachstate (lib/libthr/thread/thr_attr.c), which returns EINVAL when the variable is null or holds no attribute object.
  • The numbers. FreeBSD's <pthread.h> defines the two states as 0 and 1. The OpenOrbis homebrew SDK header (include/orbis/_types/pthread.h) defines ORBIS_PTHREAD_CREATE_JOINABLE and ORBIS_PTHREAD_CREATE_DETACHED with the same values. That header follows FreeBSD's text, so it corroborates the numbers rather than measuring them independently.

The default nobody has measured

Two detach states come from the system rather than the game: the state a fresh attribute starts with, and the one scePthreadAttrGet copies from a running thread. POSIX makes joinable the default, but nothing we can cite confirms what the PS4 reports. In FreeBSD libthr, _pthread_create (thr_create.c) uses that same default (_pthread_attr_default) when it is given no attribute variable or an empty one. The runtime treats both cases as the unknown default, so the outcome, a fatal, does not depend on the PS4 matching libthr there.

How the runtime keeps that open:

  1. Record only what was set. The attribute records a state only when one is set (has_detach_state). scePthreadAttrGet replaces the whole attribute, as libthr's pthread_attr_get_np does, so a state set before the copy is dropped.
  2. Read through one function. By convention, thread creation reads the state through rt_thread_attr_detach_state (runtime/include/runtime/process.h) and never from the field. A fresh attribute's field holds zero, which is the joinable value, so reading the field directly would assume joinable silently.
  3. Stop when there is no answer. For no variable, an empty variable, or a state nobody set, the reader stops the process (rt_fatal), names the call that asked, and says which of those cases it hit.

Sleeping

Call Status What the runtime does
sceKernelUsleep, usleep implemented Sleeps the host thread at least the requested time, then returns 0.
usleep of a second or more unresolved Stops by name.
SCE error values for sceKernelUsleep unresolved Stops by name.
sleep (libScePosix) implemented Sleeps the host thread at least the requested seconds, then returns 0 (#315, by @EzequielRindello).
sleep of more than INT_MAX seconds unresolved Stops by name.
nanosleep (libkernel) implemented Sleeps the host thread at least the requested seconds and nanoseconds, then returns 0; like usleep, an interrupted sleep resumes, so the time left is never written back (#351, by @EzequielRindello).
nanosleep with no request, nanoseconds out of range, or negative seconds unresolved Stops by name.

Both calls pause the calling thread. They take one unsigned 32-bit count of microseconds and return int. For sceKernelUsleep the game itself fixes that shape: the verified frame limiter and swap-chain present functions call it that way and expect 0 back.

How the runtime answers. A guest thread runs on a host thread, so the host thread sleeps at least the requested time and the call returns 0. A host signal is not a guest event, so an interrupted sleep resumes with the time left.

What stays open, and each stops by name rather than guessing:

  • usleep with 1,000,000 or more. Old SUSv2 allowed EINVAL there; FreeBSD sleeps. No PS4 source says which the guest gets.
  • Any SCE error value for sceKernelUsleep. The game's call sites never check the result, and no public source names one.
  • sleep of more than INT_MAX seconds. FreeBSD's libc sleeps INT_MAX seconds and returns the rest; POSIX has no early return without a signal; no PS4 source says which the guest gets.
  • nanosleep with negative seconds. POSIX doesn't define it, FreeBSD returns 0 at once, and no PS4 source says which the guest gets. Its error cases stop too, since the runtime doesn't model errno.

Stack protector

Call Status What the runtime does
__stack_chk_fail implemented Ends the process by name; the stop is the whole contract.
_exit implemented Ends the process at once with the guest's status, as POSIX defines it (no atexit handlers, nothing flushed); under the boot harness the run is recorded as "exited with code N" first (by @EzequielRindello, #454).
__stack_chk_guard implemented (maintainer's ruling) A fixed, non-zero canary word, as other PS4 runtimes use; unbound, it read a zeroed page (#528).

Code built with the compiler's stack protector places a canary value in each protected function's stack frame. The function calls __stack_chk_fail when its saved canary no longer matches, meaning that function's stack frame was overwritten. eboot, libSceFios2.elf and libc.elf import it from libkernel.

Here the stop is the implementation: the LSB contract is void(void), the call never returns and the program ends (FreeBSD's libc reports it and aborts). So the runtime stops the process by name, and the entry counts as implemented, unlike the fail-loud diagnostics elsewhere on this page.

Not covered: the PS4's own message or crash report, which the guest cannot observe after it ends, The canary itself, __stack_chk_guard, is a separate data import. Its PS4 value is not established; since #528 the runtime gives it a fixed non-zero word (before, an unbound data import got a zeroed page).

Byte order

Network protocols send integers big-endian ("network order"); the CPU may store them the other way round ("host order"). Paleblood imports four integer conversion calls from libSceNet in eboot: sceNetHtonl, sceNetHtons, sceNetNtohl, and sceNetNtohs. Their public SCE declarations use unsigned 32-bit and 16-bit integer arguments and results. The documented contract converts between host order and big-endian network order; the reverse direction uses the same operation. For the project's AMD64 guest ABI, this is byte reversal. The four calls are pure value conversions and do not require socket or online state.

This evidence supports only these four conversions. It does not establish behavior for libSceNet sockets, name resolution, epoll, or offline-state queries. Those imports remain unimplemented until their own evidence is available.

IPv4 text to binary (sceNetInetPton)

inet_pton turns an address written as text, such as dotted decimal, into its binary form. The game was seen calling it in four places, each passing address-family value 2 (AF_INET) and using the result as an IPv4 address.

For that observed path, the implementation parses dotted-decimal text into four network-order bytes, returns 1 for a valid address and 0 for malformed text, and performs no network I/O. The original call sites support the family and output use; the parser's accepted text forms come from the public BSD inet_pton(3) contract. Other address families and PS4 null-pointer error behavior are not established, so the runtime fails loudly for those cases rather than choosing host-specific results.

Offline network control (libSceNetCtl)

The executable imports six calls from libSceNetCtl. They report connection state and let the game register a callback for state changes. Four currently provide a constrained offline behavior:

  • sceNetCtlGetState writes the disconnected value (0) and returns success. The game checks 0 and 3; the disconnected interpretation is cross-checked against the public API family. The meanings of intermediate states and PS4 error behavior for a null pointer remain unknown.
  • sceNetCtlCheckCallback returns 0; while the runtime remains disconnected, no state-change callback is due. Behavior for a connected state is not implemented or established.
  • sceNetCtlRegisterCallback stores an opaque callback and argument under a nonzero ID written to the caller's output slot. Callback invocation and PS4 error values for invalid pointers or allocation failure remain unresolved.
  • sceNetCtlUnregisterCallback removes a registration by its returned ID. PS4 behavior for unknown or repeated IDs remains unresolved and fails loudly.

The registration call sites show the callback, argument, and output-ID slot; the guest later passes the returned ID to unregister. The callback pointer is kept opaque and never called. Static call-site evidence establishes these shapes, not every PS4 error case.

sceNetCtlGetNatInfo asks what kind of network address translation the connection is behind. The game writes the structure's size (16) first and reads only the NAT type at offset 8, and only on success; on any other answer it assumes NAT type 1 itself. Offline the runtime answers "not connected" (0x80412108) and writes nothing, so the game's own fallback applies (#380). The structure's layout and the error value come from public sources of other PS4 runtimes, as facts; a size other than 16 stops by name.

sceNetCtlGetInfo is answered for the one code the game asks for, 14, which public PS4 headers name the IP address: a disconnected console has none, so the runtime answers "not connected" (0x80412108, the value sceNetCtlGetNatInfo uses) and writes nothing (#461). Any other code still stops by name: a disconnected console may still describe its device or link, and that answer is not established.

A game keeps many threads busy at once: loading, audio, rendering, the game's own logic. These calls let the game start those threads and make them wait for one another.

Starting a thread. The game describes a thread with an attribute object (stack size, scheduling policy, whether anyone will wait for it to finish), then creates it. The runtime gives each guest thread its own stack and its own copy of the game's thread-local data, then runs the game's entry function on a new host thread. The game asks for a 16 KiB stack again whenever a smaller size is refused, which is how the runtime knows the smallest size it should accept.

Waiting. A semaphore holds a count. A thread that needs a unit waits until another thread signals one. Condition variables do the same job for the POSIX side of the game's libraries. Waiters are served in the order they arrived, or, for a semaphore the game creates with priority order, by thread priority: the most urgent (smallest number) first, equal priorities in arrival order (#426). Before that change a second waiter on such a semaphore stopped the boot by name, which happened in some boots and not others, depending on thread timing.

Ending a thread. A thread can end itself early with scePthreadExit. The runtime cannot unwind the game's stack frames with the host's tools, so it marks the point where it starts the game's entry function and jumps back there: the thread then ends exactly as if its entry had returned, keeping the value for a join and running its per-thread destructors (#389). It uses the compiler's own setjmp/longjmp: the C library's checked longjmp, which some compilers switch on by default, can refuse a jump from the game's stack to the host's (#399).

Thread handles fit in 40 bits. The game's own lock code stores the owner thread's handle in only 40 bits, then compares it with the full handle. A handle above 2^40 would never match, and the thread would wait forever on a lock it already held. A local boot hung exactly there. The host's memory lies above that limit, so the runtime now places its thread objects in a range below it.

Priorities. Every thread has a priority from 256 (most urgent) to 767. The game never declares its main thread's priority, so it starts at the console's default, 700; new threads inherit their creator's, and the game then sets each one explicitly. The runtime records them; your computer's own scheduler decides which thread runs.

Signal masks. The C library saves and restores each thread's set of blocked signals whenever the game uses setjmp and longjmp. No signal is delivered to the game yet, so the runtime keeps the set for each thread and gives it back unchanged.

The PS4 has two kinds of memory a game asks for. Direct memory is physical memory: the game first reserves a range of it, then maps that range into its address space, and two maps of the same range see the same bytes. Flexible memory is memory the system simply hands over.

The runtime backs direct memory with one shared host memory file, so the "same bytes" rule holds. The pool's size is the runtime's choice, not a measured PS4 value. The game maps some memory for both the CPU and the GPU. The runtime accepts the GPU flags and maps the memory for the CPU; with the display on, the renderer hands the same memory to your GPU (see "Where maps go" below). The PS4 limits how much flexible memory a game may use; that budget is not established, so the runtime does not enforce one.

Asking about memory. The game sometimes asks whether a piece of memory it mapped can be read by the CPU or by the GPU. The runtime remembers every mapping with the access the game asked for, including GPU access, and answers from that. Asked for a start and an end too, it gives the mapping's first address and the address just past its last byte (#422), as other PS4 runtimes answer; the game's movie code asks this way. A direct map can also be asked for at a particular address, and goes exactly there when that range is free.

Mapping memory twice. The movie code maps part of its own direct memory a second time, with the "no-overwrite" flag and no address. That flag only forbids replacing memory that is already mapped, which the runtime never does anyway, so it is accepted and the second map shows the same bytes as the first (#423).

Where maps go. When the game lets the system pick the address, a map the GPU will read goes at a fixed base plus its place in the pool, so the renderer can give the GPU the whole pool as one buffer and reach every such address at one fixed distance. Other maps go anywhere free above that region, and an address the game asks for is kept (#348). A boot maps each range once, so a second GPU-visible map of a range, which would need the same place, stops by name.

Bounds. A reservation must fit wholly inside the range the game searches, and a map must fit inside one reservation. The runtime checks lengths by subtraction, so a huge length cannot wrap around the end of the address space and slip past the checks (#226, by @evill33t). These are the runtime's own limits; the PS4's error codes for such calls are not established.

Bloodborne mixes its sound in eight channels (7.1) and hands the console one block of 256 samples at a time, 48,000 samples a second. Decoding. The game's sounds are stored compressed as ATRAC9, and its sound engine (FMOD) hands them to the console's audio job manager in batches of jobs: set up a decoder, then decode so many frames into a buffer. The runtime runs each batch when the game starts it and decodes with LibAtrac9 (MIT, by Alex Barney, included unmodified in Paleblood) (#398). The tests use a stand-in decoder, because no ATRAC9 data may be kept in the repository.

Playing it. Boots are silent by default. With --audio host each port plays through SDL3 on your default sound device, each channel at the volume the game set, and the output call waits while more than four blocks are queued, so the game's audio runs at your device's pace (#406). In the maintainer's local runs the game's own music and sounds start after about 17 seconds; that is an observation, not a saved record.

The movie player's sound gets a port of its own: 1024 samples at 48 kHz, in a format chosen from the movie's channel count (#420).

  • The game creates its ATRAC9 decoders at 0x01118d9a, with one to eight channels, 16-bit samples and gapless looping. The movie's port is opened at 0x02c225ae and 0x02c22842.

  • The output format is the game's own evidence: its callback at 0x0111b600 asks for format 4 | (channels == 8), so 5 is float with eight channels.

Movies

Call Status What the runtime does
sceAvPlayerInit, …PostInit, …AddSource, …Start, …Stop, …Close and the other movie player calls implemented Opens the movie from your copy and decodes it with FFmpeg on your computer (#419).
sceAvPlayerGetVideoDataEx, sceAvPlayerGetAudioData implemented Hand the game each picture and block of sound when the movie's clock reaches it.

The game plays its movies (H.264 video with AAC sound in several languages) through the console's movie player, all from one wrapper in the executable. It opens a movie, waits until it is ready, picks one video stream and the sound in your language, starts it, then asks for a picture each frame and for sound on its audio thread.

The runtime decodes a few frames ahead on a thread of its own, so the decoder never runs on one of the game's small thread stacks, and the game's calls only copy finished pictures and sound into the game's buffers, on the movie's clock. A movie that loops starts again; one that does not ends with a "stopped" event. FFmpeg is optional when building Paleblood: without it, opening a movie stops by name.

  • The wrapper's calls are at 0x02cfdf33-0x02d004a9. Pictures are NV12, in a buffer from the game's own texture allocator.
  • Layouts, event numbers and error values come from public sources of another PS4 runtime, checked against the OpenOrbis AvPlayer.h; the code is the runtime's own.

Each frame the game asks video out to show one of its frame buffers, then waits on an event queue until the console reports that the flip happened, or reads the flip status until it catches up. The runtime keeps the buffers and answers every flip straight away, so the game's frame loop can run. Each buffer also has a frame on your side, which the flip shows: in a window with --display window (SDL3 and Vulkan), or written to image files with --display-capture DIR (#313). Since #369 the runtime's own renderer draws into those frames when the game submits its GPU work, and since 6 November 2026 the maintainer's local runs show the studio logos and the title screen there (#441, #442). With the display off they are not drawn.

Flips no longer hold up the next frame (#572, 11 November). About half of the maintainer's local boots stopped on a corrupted command buffer. Instrumented boots showed the engine's render thread presenting a frame while its main thread drew the movie layer into the same graphics context: the main thread only sleeps a fixed 20 ms first. Each present waits for a free display buffer, that is for an earlier flip, and those flips were held on the renderer's thread for up to a vertical blank, so presents slid into the main thread's drawing. As on the PS4, whose GPU hands a flip to the display and goes on, flips after a frame's work are now queued to a video out thread. In four of four local boots with the character creation script the corruption did not return. A renderer frame slower than the frame budget can still delay the present, and the flip status's times and pending counts are still not modelled.

  • The two setups are at 0x015e488e and 0x02ad61d4; the flip loops at 0x015e419a and 0x02ad6ee9. The game's frame loop flips with vsync (mode 1) through sceGnmSubmitAndFlipCommandBuffers (#310); the other flips use mode 2 (hsync).

Now each buffer the ring points to goes to the renderer like a graphics buffer: with the display on its dispatches run on the GPU in submission order, with the graphics work, and its "work done" values are written after them; with the display off they are written at once, as before. Since #470 the renderer takes each buffer's recorded calls and drops them, so their shader bindings cannot leak into a later graphics buffer in the same memory.

Paleblood does not emulate the PS4's graphics chip. It will rebuild the graphics at the level of the game engine's own drawing interface, so the graphics-driver calls only need to answer what the engine expects back. The first one asks where the GPU keeps its tessellation factors (the data it uses to split surfaces into finer triangles); the engine then maps memory at that address. The PS4 answers a fixed address of its own; the runtime answers one it reserves, because nothing but the engine's own graphics code ever uses it.

The next call validates a command buffer, and the engine treats one particular error code as "this console cannot validate". Paleblood has no validation layer, so it gives that answer (#297).

The temporary GPU stand-in. The game hands work to the GPU through compute queues: it writes a pointer to each finished command buffer into a ring, then rings a "doorbell" (sceGnmDingDong). Each command buffer the game sent during start-up holds the same few steps: set shader registers, run a compute shader, then write a "work done" value to memory, which the CPU waits for. Until the engine's own renderer replaces this layer, the doorbell completes the work at once (#302): it follows each buffer, skips the shader steps (nothing is drawn or computed), writes the "work done" value and moves the queue's read position on. Any other kind of step stops by name. This keeps start-up moving; it does not make anything appear on screen. Since #606 (11 November), with the display on, the compute queues' dispatches run on the GPU instead: character creation's lit preview needs what they make (a colour volume, composed images and its light data).

What the stand-in skips safely. As the boot went further, the frame's command buffers held more kinds of packets. The stand-in skips only those that change nothing it would have to model: an empty constant-buffer entry (#375), a memory read that only warms the GPU's cache and the size of an index (#377), and an indexed draw's packets (#395). Any other form still stops by name.

The renderer alongside it. The drawing itself does not happen here. When the game binds a shader through sceGnmSetVsShader, sceGnmSetPsShader or sceGnmSetCsShader, the runtime also hands the shader's registers to Paleblood's renderer (#412, #418), and the game's own GPU library functions report its draws (see The renderer). At each submit the renderer runs what was recorded for that buffer on your GPU, and the stand-in still writes the "work done" values the game waits for.

Where the engine meets the GPU. Every one of the game's 50 graphics-driver imports is reached through one thin engine wrapper, with one or two callers each, and none of them draws anything. Bloodborne builds its GPU command buffers itself, with the graphics library compiled into the game, and only hands finished buffers to the system to run and to put on screen. So the runtime cannot take over drawing at the system-call boundary: the graphics have to be rebuilt above it, in the engine's own renderer (its GX graphics framework). The full map is on issue #39.

The former startup stop: CPU affinity

Call Status What the runtime does
scePthreadAttrGetaffinity implemented Answers the ruled mask since #561 (11 November), 0x3f by default since #585. From #207 the C library's probe no longer called it; since #571 it does again. The boot of 19 October stopped here; the boot of 4 November passes it.

A thread's CPU affinity mask says which CPU cores it may run on, one bit per core. The boot of 19 October stopped when the bundled libc.elf asked for the main thread's mask.

What the caller does. It is understood from the hash-pinned module:

  1. Copy the attributes. It copies the current thread's attributes.
  2. Ask for the mask. It passes the attribute variable and an eight-byte zeroed slot: two pointers, not FreeBSD's three-argument form with a size.
  3. Count the cores. It ignores the result, counts the set bits in the slot, and stores that count.

Synthetic runs of that original caller with scripted imports confirm this. They are not observations of PS4 affinity.

Why the runtime did not answer at first. Returning success with a guessed mask would change the CPU count the C library stores without implementing the query. So the import stayed unbound while the main thread's real mask, the exact output width and the error contract were unknown. Issue #34 tracked it. BluePinetree claimed the work: a way for the runtime to replace a function inside a bundled module such as libc.elf, so this probe could be answered there.

How it was answered (#207, by BluePinetree, merged 3 November 2026). The runtime can now replace a function inside a bundled module before any of its code runs: it writes a jump at the function's start to a small stub just past the module's image. Two replacements are listed in game/module_hooks.csv for the pinned libc.elf:

  • the thread-count probe described above returns at once, so scePthreadAttrGetaffinity is never called and the stored core count stays as it was (no mask is invented; this hook was dropped in #571, below);
  • std::thread::hardware_concurrency, which would read that count, stops the run by name if the game ever calls it, the same way an unimplemented import stops it.

Since #456 (also by BluePinetree) each entry also lists the function's first bytes, and pbboot compares them with the loaded module before patching: a different libc.elf build is refused by name before any game code runs, instead of patching the middle of another function.

The boot recorded on 4 November 2026 (#295) confirms it: merged main now passes this point; later the same day (#300) it reaches the video out milestone. The hooks only cover these two functions, and their offsets fit only the pinned libc.elf.

What it answers now (#561, merged 11 November 2026). The console's own mask is still not measured. On 10 November the maintainer ruled that a thread whose mask the game never set answers all ones, as scePthreadGetaffinity already did (on 11 November a second ruling made the default 0x3f, below). So scePthreadAttrGetaffinity(attr, mask) writes eight bytes: the mask set on the attribute with scePthreadAttrSetaffinity, or the thread's mask that scePthreadAttrGet copied (from its creation attribute or scePthreadSetaffinity), otherwise UINT64_MAX. A variable holding no attribute is EINVAL; no variable for the mask stops by name. The host's CPUs are not consulted. @evill33t's #239 did the groundwork, taking the value from the host, which the ruling replaced. The tests (test/syslib/attr_affinity.c) check a fresh attribute with canaries around the eight bytes, set masks up to bit 63, copies from threads with and without a mask, and the two error paths; four planted mistakes are caught. The probe hook above stays, so the game's CPU count does not change; whether to drop it and let the probe count the ruled mask is a separate decision.

The probe runs again (#571, merged 11 November 2026; default 0x3f since #585). The maintainer decided to drop the probe's hook, so the original probe runs in libc.elf's start-up code, before any of the executable's code. It asks scePthreadAttrGetaffinity about a copy of the main thread's attributes, which have no mask set by the game yet, counts the set bits and stores the count at libc.elf+0xd1c54. On 11 November the maintainer ruled that the default mask is 0x3f, the six CPUs 0 to 5: the mask the executable's own thread setup gives each thread. Both scePthreadGetaffinity and scePthreadAttrGetaffinity answer it for a thread or attribute with no mask. A local boot without a display read 6 from the running process (64 under the first ruling, 0 while the hook was in place). That count follows from the ruling; the console's own mask is still not measured. The second hook stays: std::thread::hardware_concurrency, the count's only reader found, still stops the run by name, so nothing reads the ruled count as if it were the console's. The boot recorded with #571 shows 248 imports called, up from 243.

Implementation and tests

  • Implement only behavior supported by public documentation, independent reverse engineering, or observed behavior.
  • Keep unresolved target behavior visible; do not fabricate a return value to make tools/boot.py advance.
  • Add cases for each established behavior and error path in a test file of the group's own, test/syslib/<group>.c, as SYSLIB_TEST(name) { ... } blocks (#407; test/syslib/np_trophy.c is an example), so parallel pull requests do not edit the same lines. Cases already in test/test_syslib.c may be updated there.
  • Runtime-only contributions do not need a game dump, captures, or function-level verify.py results; CI builds and runs the runtime and syslib tests.
