Runtime system-call notes

What each runtime system call is for, what it must do, what the game was seen to do with it, and how Paleblood's runtime answers.

At a glance

Covers
Calls from runtime issue #34, the start-up services from #36 and #40, and the network slice from #41. A generated list of every registered call is near the end.
Status
implemented: the runtime answers the call. unresolved: no established answer, so the runtime has no implementation or stops by name. observed: seen in a real boot, not yet implemented.
How to read
Each group starts with a status table, then explains the calls. PRs, citations, call-site addresses and "what would settle it" notes are in the collapsibles.
Caution
A platform manual describes that platform; it does not prove every detail of the PS4 implementation. These notes separate documented behavior from what remains unknown for the target.

Two rules the runtime follows

Most calls below share the same shape, so it helps to know it first.

  • Stopping by name. When the PS4's answer to a call is not established, the runtime does not guess. It stops the process (a "fail-loud diagnostic") and names the call the guest made. A registry entry that stops like this is not an implementation.
  • Two error conventions. Many calls exist under an SCE name (scePthread…) and a POSIX name (pthread_…). As with the mutex functions (runtime/syslib/kernel_mutex.c), the SCE name returns 0x80020000 plus the error number, and the POSIX name returns the number itself.

Time and process

Call Status What the runtime does
getpagesize unresolved Stops by name; the PS4 page size is not established.
getpid unresolved Not implemented yet; the guest-visible ID is unknown.
clock_gettime unresolved Not implemented yet; accepted clock IDs are unknown.
gettimeofday unresolved Not implemented yet; target layout and errors are unknown.

What the calls are for

getpagesize
Takes no arguments and returns the system's memory page size in bytes. The number is platform-specific. It is not in current POSIX; portable code uses sysconf(_SC_PAGESIZE).
getpid
Takes no arguments and returns a pid_t for the calling process. POSIX defines no error return. What a process ID means, and how long it lives, is platform-specific.
clock_gettime
Reads the clock chosen by clock_id into a struct timespec: seconds (tv_sec) and nanoseconds (tv_nsec, from 0 through 999,999,999). POSIX returns 0 on success, and -1 with errno on failure; an unsupported clock ID is EINVAL.
gettimeofday
Reads wall time into a struct timeval: seconds since the Epoch and microseconds (tv_usec from 0 through 999,999). Wall time can jump, so it is not a monotonic clock for measuring elapsed time. POSIX.1-2024 removed the interface.

What the game does with them

The executable imports getpagesize and gettimeofday from libScePosix. The game's bundled libc.elf imports clock_gettime, getpagesize, getpid, and gettimeofday from libkernel. These imports tell us which names are needed, not every argument or how the PS4 behaves.

  • The frame limiter reads the time with gettimeofday and passes null for the timezone argument.
  • A separate verified game helper calls sceKernelClockGettime with clock ID 4, identified as CLOCK_MONOTONIC. That confirms the ID for the SCE entry point only. It does not show which IDs the game passes to the imported clock_gettime wrapper, or whether 4 is accepted there.

Clock ID numbers are implementation-defined. Linux and FreeBSD each have their own sets, and their numbers are not evidence for the PS4.

Working out the page size

The page size is a good example of how far file evidence goes, and where it stops. getpagesize is the only page-size query the game has: nothing imports sysconf.

  1. Observed in the game files. Every loadable segment of the eight images is aligned to 0x4000, and each segment's file offset and address differ by exactly 0x4000. Three call sites use the result the same way: they accept it only if it is a power of two and cache it next to three fixed sizes (0x10000, 0x40000, 0x200000). Nothing else reads that cached value, and nothing compares it with a constant.
  2. Inferred, with its assumptions. If the PS4 loader follows the usual ELF rules for these segments, the page size cannot be larger than 0x4000; any power of two that divides 0x4000 would fit. Narrowing that to 4 KiB, 8 KiB or 16 KiB also assumes a page is at least 4 KiB, which is our assumption, not an observation. The game's own check accepts every power of two, so it does not pick one either.
  3. Unknown. The actual value. Stock FreeBSD on AMD64 uses 4096, but that describes the PS4 kernel's ancestor, not the console.

So both getpagesize entries stop by name. Paleblood's loader does not depend on the page size: it copies each segment to its exact address. Never substitute the build host's page size without evidence.

Threads and yielding

Call Status What the runtime does
scePthreadEqual implemented Compares guest thread handles; zero means different.
sched_yield implemented Yields the host thread and returns zero.
scePthreadYield unresolved Stops by name; the PS4 return signature is unknown.
pthread_self implemented Answers what scePthreadSelf answers.

A guest thread runs on a host thread. A thread handle is an opaque pointer to the runtime's object for that thread, so these calls work by comparing or returning those pointers.

  • scePthreadEqual asks whether two handles name the same thread. The runtime compares the opaque object pointers used as guest thread handles: zero means different, nonzero means equal. The exact nonzero value the PS4 returns, and its behavior for a null handle, are not established.
  • sched_yield lets other threads run. The runtime yields the calling host thread and returns zero, following the POSIX/FreeBSD contract. A host failure stops by name. The unit test checks the result; it cannot prove that the host scheduler ran another thread.
  • scePthreadYield sounds like the same thing, but it stays unresolved. FreeBSD's analogue returns void, while Linux's returns int, and nothing settles which one the PS4 uses. It is registered with RT_SYSLIB_UNRESOLVED and stops by name; registry presence is not implementation evidence.
  • pthread_self (libScePosix) returns the calling thread's own handle. It answers exactly what scePthreadSelf answers. With no guest thread registered on the host thread, it stops by the name the guest used. POSIX defines no error return.

These are runtime services, not new decompiled game functions, and the saved boot has not been rerun to demonstrate their startup effect.

Thread attributes

Call Status What the runtime does
scePthreadAttrSetdetachstate, pthread_attr_setdetachstate implemented Records the state; bad values give EINVAL.
Default detach state (fresh or copied attribute) unresolved Thread creation stops by name instead of assuming joinable.
pthread_attr_init, pthread_attr_destroy implemented Allocate and free attributes under the POSIX names.

A thread attribute is a small object a program fills in before creating a thread: it describes how the new thread should start. The game creates and frees these objects, and sets one field of them, the detach state.

Creating and freeing attributes

eboot imports pthread_attr_init and pthread_attr_destroy from libScePosix, next to the SCE names the runtime already had.

  • Init allocates the attribute and stores it in the variable; ENOMEM when it cannot (POSIX; FreeBSD libthr's _pthread_attr_init).
  • Destroy frees it and empties the variable; EINVAL for a missing or empty variable (libthr's _pthread_attr_destroy).
  • A missing variable passed to init is undefined in POSIX and unchecked in libthr. The runtime answers EINVAL under both names, as the SCE name already did and as the mutex attribute calls do. No PS4 source or call site says otherwise.

An attribute made under one name can be freed under the other.

Setting the detach state

eboot and libSceFios2.elf import scePthreadAttrSetdetachstate from libkernel, and eboot imports pthread_attr_setdetachstate from libScePosix (symbols/imports.csv).

  • What the call does. A thread created with the attribute starts detached for PTHREAD_CREATE_DETACHED (nobody waits for it to finish) and joinable for PTHREAD_CREATE_JOINABLE (another thread can join it). This is POSIX pthread_attr_setdetachstate.
  • Invalid detach state. POSIX and FreeBSD's pthread_attr(3) both make any other value EINVAL.
  • Invalid attribute variable. POSIX leaves a null or uninitialised attribute undefined and only recommends EINVAL, and the FreeBSD manual lists no error for it. The behaviour comes from FreeBSD libthr's _pthread_attr_setdetachstate (lib/libthr/thread/thr_attr.c), which returns EINVAL when the variable is null or holds no attribute object.
  • The numbers. FreeBSD's <pthread.h> defines the two states as 0 and 1. The OpenOrbis homebrew SDK header (include/orbis/_types/pthread.h) defines ORBIS_PTHREAD_CREATE_JOINABLE and ORBIS_PTHREAD_CREATE_DETACHED with the same values. That header follows FreeBSD's text, so it corroborates the numbers rather than measuring them independently.

The default nobody has measured

Two detach states come from the system rather than the game: the state a fresh attribute starts with, and the one scePthreadAttrGet copies from a running thread. POSIX makes joinable the default, but nothing we can cite confirms what the PS4 reports. In FreeBSD libthr, _pthread_create (thr_create.c) uses that same default (_pthread_attr_default) when it is given no attribute variable or an empty one. The runtime treats both cases as the unknown default, so the outcome, a fatal, does not depend on the PS4 matching libthr there.

How the runtime keeps that open:

  1. Record only what was set. The attribute records a state only when one is set (has_detach_state). scePthreadAttrGet replaces the whole attribute, as libthr's pthread_attr_get_np does, so a state set before the copy is dropped.
  2. Read through one function. By convention, thread creation reads the state through rt_thread_attr_detach_state (runtime/include/runtime/process.h) and never from the field. A fresh attribute's field holds zero, which is the joinable value, so reading the field directly would assume joinable silently.
  3. Stop when there is no answer. For no variable, an empty variable, or a state nobody set, the reader stops the process (rt_fatal), names the call that asked, and says which of those cases it hit.
Thread attributes: PRs, credits and tests

Merged PR #95, by @EzequielRindello, registers pthread_attr_init and pthread_attr_destroy, following the same split as the mutex and detach-state calls: the POSIX names return the FreeBSD error number itself, the SCE names 0x80020000 plus it, and an attribute made under one name can be freed under the other.

Default detach state: what would settle it

An observed scePthreadAttrGetdetachstate result on a console, for a fresh attribute and for one filled by scePthreadAttrGet from the main thread. Guest call sites would also settle it: a thread created without a detach state being set, then joined or detached (scePthreadJoin, pthread_join and scePthreadDetach are imported).

Sleeping

Call Status What the runtime does
sceKernelUsleep, usleep implemented Sleeps the host thread at least the requested time, then returns 0.
usleep of a second or more unresolved Stops by name.
SCE error values for sceKernelUsleep unresolved Stops by name.

Both calls pause the calling thread. They take one unsigned 32-bit count of microseconds and return int. For sceKernelUsleep the game itself fixes that shape: the verified frame limiter and swap-chain present functions call it that way and expect 0 back.

How the runtime answers. A guest thread runs on a host thread, so the host thread sleeps at least the requested time and the call returns 0. A host signal is not a guest event, so an interrupted sleep resumes with the time left.

What stays open, and each stops by name rather than guessing:

  • usleep with 1,000,000 or more. Old SUSv2 allowed EINVAL there; FreeBSD sleeps. No PS4 source says which the guest gets.
  • Any SCE error value for sceKernelUsleep. The game's call sites never check the result, and no public source names one.
Sleeping: PR, credits and tests

Merged PR #94, by @EzequielRindello, implements both.

The tests measure that each call lasts at least what was asked on the host's monotonic clock.

Stack protector

Call Status What the runtime does
__stack_chk_fail implemented Ends the process by name; the stop is the whole contract.
__stack_chk_guard unresolved Separate data import; currently gets a zeroed page.

Code built with the compiler's stack protector places a canary value in each protected function's stack frame. The function calls __stack_chk_fail when its saved canary no longer matches, meaning that function's stack frame was overwritten. eboot, libSceFios2.elf and libc.elf import it from libkernel.

Here the stop is the implementation: the LSB contract is void(void), the call never returns and the program ends (FreeBSD's libc reports it and aborts). So the runtime stops the process by name, and the entry counts as implemented, unlike the fail-loud diagnostics elsewhere on this page.

Not covered: the PS4's own message or crash report, which the guest cannot observe after it ends, and __stack_chk_guard, the canary value itself. That is a separate data import whose PS4 value is not established; an unbound data import currently gets a zeroed page.

Stack protector: PR and credits

Merged PR #97, by @EzequielRindello, stops the process by name.

Memory operations

Call Status What the runtime does
memcpy, memset implemented ISO C copy and fill; both return the destination.

These are the two ISO C operations imported by libSceFios2.elf from libSceLibcInternal. memcpy copies the requested bytes, and memset writes a value, converted to an unsigned byte, across a region. Both return the destination. Undefined cases such as overlapping memcpy regions and null pointers are not modeled.

Memory operations: PR and tests

Merged PR #82 supplies both. The registry tests cover the returned pointer, zero length, byte truncation, untouched bytes past the requested region, and coverage classification. These tests do not establish additional PS4 behavior or a new boot milestone.

Byte order

Network protocols send integers big-endian ("network order"); the CPU may store them the other way round ("host order"). Paleblood imports four integer conversion calls from libSceNet in eboot: sceNetHtonl, sceNetHtons, sceNetNtohl, and sceNetNtohs. Their public SCE declarations use unsigned 32-bit and 16-bit integer arguments and results. The documented contract converts between host order and big-endian network order; the reverse direction uses the same operation. For the project's AMD64 guest ABI, this is byte reversal. The four calls are pure value conversions and do not require socket or online state.

This evidence supports only these four conversions. It does not establish behavior for libSceNet sockets, name resolution, epoll, or offline-state queries. Those imports remain unimplemented until their own evidence is available.

IPv4 text to binary (sceNetInetPton)

inet_pton turns an address written as text, such as dotted decimal, into its binary form. The game was seen calling it in four places, each passing address-family value 2 (AF_INET) and using the result as an IPv4 address.

For that observed path, the implementation parses dotted-decimal text into four network-order bytes, returns 1 for a valid address and 0 for malformed text, and performs no network I/O. The original call sites support the family and output use; the parser's accepted text forms come from the public BSD inet_pton(3) contract. Other address families and PS4 null-pointer error behavior are not established, so the runtime fails loudly for those cases rather than choosing host-specific results.

Offline network control (libSceNetCtl)

The executable imports six calls from libSceNetCtl. They report connection state and let the game register a callback for state changes. Four currently provide a constrained offline behavior:

  • sceNetCtlGetState writes the disconnected value (0) and returns success. The game checks 0 and 3; the disconnected interpretation is cross-checked against the public API family. The meanings of intermediate states and PS4 error behavior for a null pointer remain unknown.
  • sceNetCtlCheckCallback returns 0; while the runtime remains disconnected, no state-change callback is due. Behavior for a connected state is not implemented or established.
  • sceNetCtlRegisterCallback stores an opaque callback and argument under a nonzero ID written to the caller's output slot. Callback invocation and PS4 error values for invalid pointers or allocation failure remain unresolved.
  • sceNetCtlUnregisterCallback removes a registration by its returned ID. PS4 behavior for unknown or repeated IDs remains unresolved and fails loudly.

The registration call sites show the callback, argument, and output-ID slot; the guest later passes the returned ID to unregister. The callback pointer is kept opaque and never called. Static call-site evidence establishes these shapes, not every PS4 error case.

The other two stay unresolved and are registered only to produce a useful fatal diagnostic:

  • sceNetCtlGetInfo: the PS4 structure layout, module-14 meaning, and offline answer are unknown.
  • sceNetCtlGetNatInfo: the guest writes a 16-byte size and later reads offset 8, but the PS4 meaning of that field and offline NAT value are unknown.

Their registry presence does not mean they are implemented.

System modules (libSceSysmodule)

Call Status What the runtime does
sceSysmoduleLoadModule, sceSysmoduleIsLoaded, sceSysmoduleUnloadModule implemented Answer for stub modules only; every other case stops by name.

A system module is a PS4 library the game can ask for at run time. The executable asks for system modules by id through sceSysmoduleLoadModule, sceSysmoduleIsLoaded and sceSysmoduleUnloadModule; it imports no other loader entry.

Five of the seven modules the title ships are recorded in Paleblood's module list as stubs: the executable imports nothing from them, so they are not mapped. Their public ids come from the OpenOrbis toolchain's list.

How the runtime answers, for stub modules only:

  1. A load marks the module loaded and succeeds without mapping anything.
  2. A query of a loaded one answers 0.
  3. An unload clears the mark.

Everything else stops by name: a module that is not a stub (the runtime cannot load system modules yet), a second load of a loaded stub, and a query or unload of a stub that is not loaded. The error values for those cases are not public. The saved boot stops before the first load, so which ids the game passes is not yet observed.

System modules: PR and credits

Merged PR #83, by @adurham, answers those three calls for the stub modules only.

Creating threads and waiting

Call Status What the runtime does
scePthreadCreate implemented Runs the guest's entry on a new host thread with its own stack and thread-local storage.
scePthreadSetaffinity implemented Records the CPU mask; the host schedules the thread.
scePthreadAttrSetstacksize, pthread_attr_setstacksize implemented Records the size; below 16 KiB it answers "invalid", as the game expects.
scePthreadAttrSetschedpolicy implemented Records FIFO, other or round-robin.
sceKernelCreateSema … sceKernelPollSema implemented Counting semaphores: create, wait, signal, poll, delete.
pthread_cond_* implemented Condition variables, without timed waits.

A game keeps many threads busy at once: loading, audio, rendering, the game's own logic. These calls let the game start those threads and make them wait for one another.

Starting a thread. The game describes a thread with an attribute object (stack size, scheduling policy, whether anyone will wait for it to finish), then creates it. The runtime gives each guest thread its own stack and its own copy of the game's thread-local data, then runs the game's entry function on a new host thread. The game asks for a 16 KiB stack again whenever a smaller size is refused, which is how the runtime knows the smallest size it should accept.

Waiting. A semaphore holds a count. A thread that needs a unit waits until another thread signals one. Condition variables do the same job for the POSIX side of the game's libraries.

Thread handles fit in 40 bits. The game's own lock code stores the owner thread's handle in only 40 bits, then compares it with the full handle. A handle above 2^40 would never match, and the thread would wait forever on a lock it already held. A local boot hung exactly there. The host's memory lies above that limit, so the runtime now places its thread objects in a range below it.

Threads and waiting: PRs, call sites and what stops by name
  • PRs #144 (semaphores), #147 (condition variables), #148 (attribute setters), #149 (thread creation) and #155 (handles below 2^40).
  • The 16 KiB retry is at 0x02a3b383; the 40-bit lock is at 0x024368c0.
  • Stops by name: creating a thread without an attribute, a stack size or a detach state; a stack the guest supplies; an empty CPU mask; a semaphore wait with a timeout; a second waiter woken by priority; timed condition waits.

Memory: direct and flexible

Call Status What the runtime does
sceKernelGetDirectMemorySize implemented Answers the size of the runtime's own pool (5 GiB).
sceKernelAllocateDirectMemory implemented Hands out a range of the pool.
sceKernelMapDirectMemory implemented Maps an allocated range for the CPU; GPU access is accepted.
sceKernelReleaseDirectMemory implemented Gives a whole, unmapped range back.
sceKernelMapFlexibleMemory implemented Maps fresh zeroed memory that is not part of the pool.

The PS4 has two kinds of memory a game asks for. Direct memory is physical memory: the game first reserves a range of it, then maps that range into its address space, and two maps of the same range see the same bytes. Flexible memory is memory the system simply hands over.

The runtime backs direct memory with one shared host memory file, so the "same bytes" rule holds. The pool's size is the runtime's choice, not a measured PS4 value. The game maps some memory for both the CPU and the GPU. The runtime has no GPU yet, so it accepts the GPU flags and maps the memory for the CPU only. The PS4 limits how much flexible memory a game may use; that budget is not established, so the runtime does not enforce one.

Memory: PRs, call sites and what stops by name
  • PRs #143 (direct memory), #154 (GPU access) and #156 (flexible memory).
  • The game's maps use protection 3 (CPU read and write) and 0x33 (CPU and GPU read and write); its only flexible map is at 0x02481dbe.
  • Stops by name: map flags and address hints, other protection bits, lengths that are not whole 16 KiB pages, a range that does not fit, and releasing part of a range or a mapped one.

Console services at start-up

Call Status What the runtime does
sceUserServiceInitialize, …GetInitialUser, …GetLoginUserIdList implemented One user, logged in from the start.
sceCommonDialogInitialize implemented Succeeds once; a repeat answers "already initialized".
sceSystemServiceParamGetInt implemented Answers the console language you choose (English, United States, by default).
sceAppContentInitialize, sceAppContentAppParamGetInt implemented Answers the title's own parameters from your copy's param.sfo.
sceNpSetContentRestriction implemented Records nothing: the runtime is offline and has no online content.

Before the title screen the game asks the console a few questions: who is playing, which language to use, and what its own package says about itself.

  • The user. The runtime models one user, the person running it, logged in from the start.
  • The language. The language is a console setting, so you choose it: tools/boot.py --system-param 1=18 picks English (United Kingdom), for example.
  • The title's parameters. These come from your own copy's param.sfo. Paleblood ships none.
  • Repeats. The game initializes some services twice. In each case its second call accepts one exact "already initialized" error, and the runtime answers that error.
Console services: PRs, call sites and what stops by name
  • PRs #146 (app content), #150 (user service), #151 (common dialog), #152 (system language) and #153 (content restriction).
  • The "already initialized" answers are 0x80960003 (user service, accepted at 0x010ba1ac) and 0x80b80002 (common dialog, accepted at 0x02023fbb). All nine language reads ask for setting 1.
  • Stops by name: a service call before initialize, a setting nobody gave, a title parameter your copy does not declare, and missing arguments.

The current startup stop

Call Status What the runtime does
scePthreadAttrGetaffinity observed Left unbound; the latest genuine boot stops here.

A thread's CPU affinity mask says which CPU cores it may run on, one bit per core. The latest genuine boot stops when the bundled libc.elf asks for the main thread's mask.

What the caller does. It is understood from the hash-pinned module:

  1. Copy the attributes. It copies the current thread's attributes.
  2. Ask for the mask. It passes the attribute variable and an eight-byte zeroed slot: two pointers, not FreeBSD's three-argument form with a size.
  3. Count the cores. It ignores the result, counts the set bits in the slot, and stores that count.

Synthetic runs of that original caller with scripted imports confirm this. They are not observations of PS4 affinity.

Why the runtime does not answer yet. Returning success with a guessed mask would change the CPU count the C library stores without implementing the query. So the import stays unbound until the main thread's real mask, the exact output width and the error contract are established. Issue #34 tracks it. BluePinetree has claimed the work: a way for the runtime to replace a function inside a bundled module such as libc.elf, so this probe can be answered there.

scePthreadAttrGetaffinity: declaration source

OpenOrbis libkernel.h has the affinity declaration. It is corroboration, not a measured PS4 contract.

Implementation and tests

  • Implement only behavior supported by public documentation, independent reverse engineering, or observed behavior.
  • Keep unresolved target behavior visible; do not fabricate a return value to make tools/boot.py advance.
  • Add cases to the RT_SYSLIB unit test for each established behavior and error path.
  • Runtime-only contributions do not need a game dump, captures, or function-level verify.py results; CI builds and runs the runtime and syslib tests.
