Stats & Progression

One verified per-frame character update changes a bounded value the source calls points. It is a concrete example of how a game stat can be driven by the frame loop.

At a glance

Function
character_frame_update_01cbdb20 (0x01cbdb20), called from two character update loops.
What it does
Accumulates fractional recovery between frames, applies a character-specific rate, and clamps the result between -50 and a per-character maximum.
Status
Verified against recorded original-game calls and generated edge cases, with independent review.
Not established
That points is the player's stamina, that it belongs only to the player, or how it fits the wider progression system.

This article describes one function and its tested behavior. It is not a complete account of combat, weapon costs, attributes, leveling, or save data.

The per-frame update

character_frame_update_01cbdb20 (0x01cbdb20, 979 bytes) is called from two character update loops. In order, it:

  1. reads the character's frame time;
  2. handles a pending throw animation event when the animation-event manager is ready;
  3. updates the points value (below);
  4. passes time into a character module step;
  5. runs other module calls and copies data used by the character and animation systems.

The Character page lists the observed fields and remaining layout questions.

How points change each frame

  1. Check the flag. If the character parameter flag disables regeneration, return without changing the stat.
  2. Work out the rate. Multiply the parameter byte by 0.01, the character multiplier, and a factor returned through the character's virtual table. The result is the per-second rate.
  3. Add this frame's share. Save the rate truncated toward zero, then calculate frame time × rate + saved fraction.
  4. Split whole and fraction. Apply the whole-number portion to the current points value and keep the fractional remainder for the next update.
  5. Guard and clamp. If the change would lower points, skip it when the data flag or observed debug flag disables drops. Otherwise clamp the value to at least -50 and at most the character's maximum.

Why keep the fraction? It stops each frame from discarding the part of the recovery smaller than one point. A slower update can therefore accumulate several fractional contributions before the integer stat changes.

Frame-time variants

The update normally uses the frame time stored on the character. The community frame-rate patches substitute their own:

Mode Frame time the update uses
Original timing The frame time stored on the character
Community 30 FPS patch 1/27 second
Community 60 FPS patch 1/54 second
Uncapped patch The stored time

Paleblood's BB_TARGET_FPS option mirrors those substitutions in this function. See Frame timing for the main loop and the broader patch comparison.

Those constants explain the code path; they do not establish why the patch authors selected them or how the resulting rate feels in every game state.

How we know

The replacement is marked verified in Paleblood's function table. It was compared against two kinds of evidence, in each of four runs (original timing, 30 FPS, 60 FPS, uncapped):

  • Recorded cases: previously captured original-game calls.
  • Edge cases: generated boundary cases.

Each comparison reported zero failures, and an independent review approved the readable refactor after rerunning all recorded and edge cases.

These results support equivalence over those recorded inputs and generated cases. They do not prove every possible state, identify the points value as stamina, or establish that an enemy or boss uses this exact update. See Evidence & Media Review for how this wiki labels different kinds of evidence.

Open questions

  • What game concept does the points field represent, and which character types use it?
  • What do the associated parameter byte and virtual multiplier mean in game-facing terms?
  • Which module consumes the points value, and how does that connect to combat or progression?
  • Why do the frame-rate patches use 1/27 and 1/54 second rather than exact display-frame intervals?

Until those links are supported by source analysis or recorded evidence, “stamina” remains a hypothesis rather than the name of this mechanic.

What this page can and cannot claim

Every claim in this section is labelled by the kind of evidence behind it.

Label Meaning
observed Seen during play or in a recording, with its context: starting state, player position and actions, the visible change, and whether it repeats.
inferred A conclusion drawn from code or tests, stated with the scope that evidence covers.
unknown Not yet traced. It stays an open question, with the evidence needed next.
  • Observation is not implementation. An animation, health-bar change, phase transition, hit reaction, movement, or line of dialogue can be observed. On its own it does not identify an entity ID, function, data field, condition, timer, probability, script, or internal state.
  • No guessing. Nothing is filled in from genre convention, a gameplay impression, animation timing, or a displayed bar. Visually similar actions are not assumed to share code. No guessed names, IDs, catalogs, or numerical tables are published.
  • What a source claim needs. The entity, the function and address, the data or state it reads, the result it produces, public Paleblood source at the exact merged revision, tests, and independent review.
  • Evidence kinds differ. Recorded original-game behavior, static analysis, synthetic Paleblood tests, and verified replacements are different kinds of evidence. A link to one does not prove the others.
  • Tests have a scope. Passing tests support equivalence on the cases they cover, not untested gameplay situations. Timing and probability claims need measurements or directly verified logic, not a single encounter.
  • Shared systems are not specific actors. The verified AI, Character, Event, and Physics findings do not yet identify any particular boss, enemy, NPC, weapon, or attack.
  • Absence is not a claim about the game. A missing profile describes the project's research, not what the game contains.
