Stats & Progression

What we know so far

One verified per-frame character update changes a bounded value the source calls points. It accumulates fractional recovery between frames, applies a character-specific rate, and clamps the result between -50 and a per-character maximum. That is a concrete example of how a game stat can be driven by the frame loop. The evidence does not identify this value as the player's stamina, prove that it belongs only to the player, or explain the wider progression system.

This article describes one function and its tested behavior. It is not a complete account of combat, weapon costs, attributes, leveling, or save data.

The per-frame update

character_frame_update_01cbdb20 (0x01cbdb20, 979 bytes) is called from two character update loops. It reads the character's frame time, handles a pending throw animation event when the animation-event manager is ready, updates the points value, and passes time into a character module step. It then runs other module calls and copies data used by the character and animation systems. The Character page lists the observed fields and remaining layout questions.

The points update follows this sequence:

  1. If the character parameter flag disables regeneration, return without changing the stat.
  2. Multiply the parameter byte by 0.01, the character multiplier, and a factor returned through the character's virtual table. The result is the per-second rate.
  3. Save the rate truncated toward zero, then calculate frame time × rate + saved fraction.
  4. Apply the whole-number portion to the current points value and keep the fractional remainder for the next update.
  5. If the change would lower points, skip it when the data flag or observed debug flag disables drops. Otherwise clamp the value to at least -50 and at most the character's maximum.

The retained fraction prevents each frame from discarding the part of the recovery smaller than one point. A slower update can therefore accumulate several fractional contributions before the integer stat changes.

Frame-time variants

The update normally uses the frame time stored on the character. The community 30 FPS patch substitutes 1/27 second, the 60 FPS patch substitutes 1/54 second, and the uncapped patch keeps the stored time. Paleblood's BB_TARGET_FPS option mirrors those substitutions in this function. Those constants explain the code path; they do not establish why the patch authors selected them or how the resulting rate feels in every game state. See Frame timing for the main loop and the broader patch comparison.

Evidence and limits

The replacement is marked verified in Paleblood's function table. Its verification record, dated 2026-10-07 with source digest b243fddb1ca6589a, reports 457/457 recorded cases and 39/39 edge cases for each of four runs: original timing, 30 FPS, 60 FPS, and uncapped. Each comparison reported zero failures. The recorded suite is evidence from previously captured original-game calls; the edge suite exercises generated boundary cases. An independent review record says the readable refactor was approved and all recorded and edge cases were rerun.

These results support equivalence over those recorded inputs and generated cases. They do not prove every possible state, identify the points value as stamina, or establish that an enemy or boss uses this exact update. See Evidence & Media Review for how this wiki labels different kinds of evidence.

Open questions

  • What game concept does the points field represent, and which character types use it?
  • What do the associated parameter byte and virtual multiplier mean in game-facing terms?
  • Which module consumes the points value, and how does that connect to combat or progression?
  • Why do the frame-rate patches use 1/27 and 1/54 second rather than exact display-frame intervals?

Until those links are supported by source analysis or recorded evidence, “stamina” remains a hypothesis rather than the name of this mechanic.
