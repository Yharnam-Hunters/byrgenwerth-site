CI Setup

Both repositories run GitHub Actions on every push and pull request. Neither ever sees game data: nothing from a dump is in the repositories, and CI does not need it.

Code repository (Paleblood)

.github/workflows/ci.yml runs three jobs: a GCC/Clang build matrix, policy, and a pull-request session report.

  • build (gcc) and build (clang) — install the pinned optional Capstone dependency, configure and build with CMake, run the syslib CTest (the RT_SYSLIB unit test), then run the remaining CTest suite. The workflow also runs the harness/instruction-trace and differential-engine Python suites with each compiler and its built loader. It includes hook-table and loader tests, the plug-in contract test, synthetic executable-memory hook tests, and synthetic tracing, CFG, and mutation regressions. These tests do not run the full game-run scaffold or establish native game-run equivalence.
  • policy — rejects anything that looks like game data; validates the function tables; checks that runtime and tools name nothing specific to the game; checks that the README progress matches tools/progress.py; runs the readable-code check (addresses, raw offsets, magic numbers, and recording code); and exercises the pre-commit hooks.
  • session report — on pull requests, CI selects the concise report for runtime-only changes, the documentation report, or the full decompilation/mixed report from changed file paths. Unknown code paths fail closed to the full report. Runtime changes cannot downgrade a mixed PR. The build and policy jobs still apply to every path. These four checks are required by Paleblood's current main branch protection.

Readability and independent review

The policy job's tools/check_readable.py step is a required, merge-blocking check. It rejects mechanical transcription patterns in game/, and CI refuses any growth in the grandfathered-file list. The check does not judge whether names, structure, complexity, or comments are easy for people to follow. Before a function is marked verified, a reviewer who did not write it must assess both its verification evidence and readability; the approval is recorded in symbols/reviews.csv and the promotion tools validate that record. Paleblood's current branch protection does not require a blanket approving review on every pull request.

Function-level verification against the real game cannot run in CI, because it needs your dump. It remains required for decompilation changes and runs locally (tools/verify.py run, tools/smoke.sh). The full session report must include every replacement status change recorded for the PR and matching, non-empty, passing verify.py evidence for each replaced, edge-verified, or verified function. Runtime-only contributions do not require a dump, captures, or function-level verification. After a runtime PR merges, a maintainer runs tools/boot.py locally and posts its result on the PR.

tools/promote.py checks existing recorded and edge cases locally and requires an approved review before promotion. Comparison result files go to temporary storage; the capture library remains input-only. --dry-run leaves verification metadata and function status unchanged.

Wiki (Byrgenwerth)

.github/workflows/ci.yml installs MkDocs, rejects game data, checks that every generated file (progress data, tables, visuals) agrees with the data it comes from and that no page has a hand-typed count, builds the site with --strict, and exercises the pre-commit hooks.

Local workflow (no CI needed)

Shell
tools/install_hooks.sh            # both repositories
tools/smoke.sh                    # code repository: the pipeline on a known function
export BB_PORT_DIR=/absolute/path/to/clean-paleblood-main-at-merged-sha
tools/end_session.sh              # wiki: pull numbers from the code repository, build, check
python3 -m mkdocs serve           # wiki: preview at http://127.0.0.1:8000

For wiki validation and publication, pin BB_PORT_DIR to a clean worktree at the exact merged Paleblood revision and record its absolute path and full SHA in the shared checkpoint. Do not use the implicit sibling checkout when it may contain uncommitted or stale changes.
